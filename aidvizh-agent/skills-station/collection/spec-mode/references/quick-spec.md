# Quick Spec

Режим, который создаёт все три артефакта за один проход. Это **не отдельный тип спеки** — артефакты
идентичны стандартной Feature Spec и лежат там же.

## Что пропускается

**Только гейты одобрения между фазами.** Дословно: «auto-generates requirements, design, and tasks in a single
pass. Instead of approving each phase before the next begins, you answer clarifying questions up front and land
directly on an actionable task list.»

## Что НЕ пропускается

- **Уточняющие вопросы вперёд.** Это главная точка взаимодействия: задаются вопросы про объём, ограничения,
  границы и всё, что влияет на результат. Ответы идут **до** генерации, а не по ходу.
- Сами три артефакта.
- Возможность ревью после факта: правки допустимы, как и в стандартной спеке.

## Как идёт

1. Задаются уточняющие вопросы одним блоком.
2. По ответам генерируются `requirements.md`, `design.md`, `tasks.md` **последовательно, без пауз на одобрение**.
3. На выходе — список задач, готовый к исполнению.

Режим не переключается: обратно в стандартный Feature Spec посреди работы не перейти. Но артефакты совместимы —
дальше можно продолжать любым spec-workflow, уточнять файлы, перегенерировать задачи, ссылаться через
`#spec:<feature>`.

## Как формулировать уточняющие вопросы

До пяти, иначе смысл режима теряется. Каждый — с предлагаемым вариантом ответа, чтобы человек мог просто
подтвердить. Таксономия, по которой стоит пройтись:

| Категория | Что уточнить |
|---|---|
| Объём | что входит и что явно **не** входит |
| Данные и модель | сущности, их поля, связи, владелец данных |
| Взаимодействие | как пользователь это видит, ключевые экраны и переходы |
| Нефункциональные | объём, latency, доступность, безопасность |
| Интеграции | внешние системы, их контракты, что при их отказе |
| Границы | пустые значения, максимумы, конкурентный доступ |
| Ограничения | стек, обязательные зависимости, совместимость |
| Термины | неоднозначные слова, которые надо зафиксировать |
| Признак готовности | как поймём, что сделано |

Пропущенная категория — не всегда дыра: если вопрос не влияет на результат, его лучше не задавать.

## Когда брать

- фича понятная, результат предсказуем;
- править требования и дизайн не планируется;
- нужна скорость, а не ревью по фазам;
- стандартный поток казался слишком тяжёлым и раз за разом вытеснялся обычным разговором.

## Когда НЕ брать

- комплаенс-домены (финансы, медицина, персональные данные) — там гейты дают реальную ценность;
- системы с высокой ценой ошибки;
- незнакомая территория, где требования требуют итераций;
- когда команда выигрывает от явных точек одобрения.

## Отличие от обычного разговора

Разговор без структуры не создаёт артефактов: в `.kiro/specs/` ничего не появляется, решение остаётся в
истории чата. Quick Spec создаёт **полный** набор артефактов — просто без гейтов. После него у фичи есть
требования, дизайн и задачи, к которым можно вернуться через месяц.

## Пропустили важное требование

Правится после факта, а не переделкой спеки: дописать `requirements.md` напрямую или попросить в сессии,
затем **Sync Files** — задачи подтянутся под новое требование.

Полезно прогнать анализ требований (`/spec-analyze <feature>`): именно для quick-спеки он и рекомендован,
поскольку требования не проходили ручное ревью.
