# Steering — постоянный контекст проекта

Steering — это **память проекта**, а не исчерпывающая спецификация. Лежит в `.kiro/steering/` репозитория
или глобально в `~/.kiro/steering/` (при конфликте побеждает рабочая копия).

Спека не повторяет steering: требования и дизайн опираются на него как на данность. Стек, конвенции именования,
архитектурные решения — всё это в спеке выглядит короткой ссылкой, а не пересказом.

## Три основных файла

| Файл | О чём |
|---|---|
| `product.md` | назначение, ценность, бизнес-контекст — **не** перечень фич |
| `tech.md` | ключевые фреймворки, стандарты, конвенции — **не** весь список зависимостей |
| `structure.md` | паттерны организации, правила именования — **не** дерево каталогов |

Включаются всегда, по умолчанию.

## Настраиваемые файлы

Профильные наборы, когда у проекта есть свои стандарты: API, аутентификация, база данных, развёртывание,
обработка ошибок, безопасность, тестирование. Вес такой же, как у основных: шаблоны — точка старта, а не
обязательная форма.

## Режимы включения

Задаются YAML-фронтматтером, который должен быть **первым содержимым файла** — пустых строк выше быть не должно.

```yaml
---
inclusion: always
---
```

| Режим | Когда включается |
|---|---|
| `always` | всегда (по умолчанию) |
| `fileMatch` | при работе с файлами по шаблону: `fileMatchPattern: "components/**/*.tsx"`, может быть массивом |
| `manual` | вручную, по имени файла (появляется как отдельная команда) |
| `auto` | когда запрос совпадает с `description`; требуются поля `name` и `description` |

Ссылки на живые файлы внутри steering: `#[[file:relative/path]]`.

`AGENTS.md` поддерживается наравне: режимов включения не имеет, включается всегда, читается из глобального
steering, корня проекта и подкаталогов.

В CLI-вариантах режимы включения не поддерживаются — грузятся все файлы каталога.

Кастомные агенты steering автоматически не получают: его нужно явно перечислить в их ресурсах.

## Гранулярность

Золотое правило: **если новый код следует существующим паттернам, steering обновлять не нужно.**

Документировать:

- организационные паттерны: feature-first, слоистая структура;
- правила именования;
- стратегию импортов: абсолютные или относительные;
- архитектурные решения: управление состоянием, границы модулей;
- стандарты технологий: ключевые фреймворки.

Не документировать:

- полный перечень файлов;
- описание каждого компонента;
- все зависимости;
- детали реализации;
- каталоги инструментов агентов (`.cursor/`, `.claude/`, `.gemini/`);
- метаданные `.kiro/` — там лежат настройки, не знание о проекте.

Плохо — инвентаризация:

```md
- /components/Button.tsx — основная кнопка с вариантами
- /components/Input.tsx — поле ввода с валидацией
- ... (ещё 50 файлов)
```

Хорошо — паттерн:

```md
## UI-компоненты (`/components/ui/`)

Переиспользуемые примитивы, выровненные по дизайн-системе:
- имя по функции (Button, Input, Modal);
- экспортируется и компонент, и его интерфейс;
- бизнес-логики внутри нет.
```

Второе не устареет после добавления пятидесятого компонента, первое — устареет к следующей неделе.

## Безопасность

В steering никогда не попадают: ключи, пароли, учётные данные, строки подключения к БД, внутренние адреса,
секреты и персональные данные. Steering читается на каждом шаге и попадает в контекст модели.

## Обновление

- Добавлять, а не заменять: пользовательские разделы и примеры сохраняются.
- Проставлять `updated_at` и причину правки.
- Один файл — одна тема.
- Объём — ориентировочно 100–200 строк; больше означает, что это уже спецификация.

## Что это даёт спеке

- Дизайн не изобретает стек и конвенции: они уже объявлены, и решения сверяются с ними.
- Задачи не содержат инструкций вида «используй тот же паттерн, что в остальном проекте» — паттерн известен.
- Требования не переписывают бизнес-контекст: он в `product.md`.
- Проверка «соответствует ли дизайн принципам проекта» становится реальной, а не декларативной.
