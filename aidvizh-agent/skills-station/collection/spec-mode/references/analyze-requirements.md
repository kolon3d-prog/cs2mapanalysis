# Анализ требований

Глубокий проход по требованиям **до** дизайна. Работает поперёк всего набора, а не построчно: два требования
могут быть каждое осмысленным по отдельности и невыполнимыми вместе, и построчное чтение этого не покажет.

Запускается: `/spec-analyze <feature>`. Рекомендован после автогенерации требований — особенно после Quick
Spec, где ручного ревью не было.

Длится минуты, не секунды: рассуждение по всему множеству дороже. Для маленькой понятной спеки можно
пропустить и идти в дизайн.

## Пять категорий дефектов

### 1. Logical inconsistencies

Требования по отдельности корректны, вместе невыполнимы.

> 1.3 — «When a user updates the cart, the Checkout Service shall recalculate totals synchronously.»
> 4.1 — «When a user updates the cart, the Checkout Service shall respond within 50 ms.»

Пересчёт по всем позициям с обращением к складу в 50 мс не укладывается. Либо это асинхронный пересчёт, либо
бюджет другой — но одно из требований должно измениться.

### 2. Ambiguities

Формулировки, которые разные исполнители реализуют по-разному.

> «Система должна быстро отвечать на большие файлы.»

Что такое «большой» — мегабайты или гигабайты? Что такое «быстро»? Пока в требовании нет числа и единицы,
это не требование, а пожелание. Лечится превращением в наблюдаемое: «файл до 100 МБ — ответ в течение 2 с
для 95-го процентиля».

### 3. Conflicting constraints

Функциональное требование сталкивается с нефункциональным.

> 1.2 — «The Service shall return the full user profile in one response.»
> 6.4 — «The Service shall never return more than 100 KB per response.»

Конфликт по существу. Решается явно: либо ограничение по размеру снимается для этого эндпоинта, либо профиль
делится на страницы — и тогда меняется 1.2.

### 4. Unstated assumptions

Ссылки на концепции, которых в требованиях нет.

> «Система должна помечать записи как просроченные.»

Нигде не сказано, что значит «просроченная»: какое поле, чей часовой пояс, считается ли выходной день. Пока
определения нет, реализация появится, а требование останется невыполненным.

### 5. Missing edge cases

Happy path расписан, отказы — нет.

- Пустой ввод, максимальные значения, не-ASCII, дубликаты.
- Отказ внешней зависимости, таймаут, частичный успех.
- Конкурентный доступ: два запроса на одну запись, повторная отправка, идемпотентность.
- Прерывание посреди операции: остаётся ли система в согласованном состоянии.

Эвристика: если в документе нет ни одной строки `If`, отказы не покрыты.

## Формат находки

Каждая находка — три части, иначе человек не может принять решение:

1. **Требования-участники** — номера ID, а не цитаты целиком.
2. **Суть простым языком** — что именно не сходится и почему это проблема.
3. **Варианты исправления** — конкретные альтернативы на выбор, а не «уточните требования».

Пример:

> **1.3 ↔ 4.1** — синхронный пересчёт корзины не укладывается в бюджет 50 мс.
> Варианты: (а) пересчёт асинхронный, ответ возвращает предыдущий итог и обновляется событием;
> (б) бюджет поднят до 300 мс; (в) пересчёт по изменённым позициям, а не по всей корзине.

Ответы применяются к `requirements.md` сразу. Неоднозначность признана намеренной — фиксируется отказом
(dismiss) и в правки не идёт.

Повторный запуск после ручных правок перепроверяет затронутые требования и их взаимодействия, а не весь
документ заново.

## Когда обязательно

- сложная фича, где требований много и они взаимодействуют;
- домены с ценой неоднозначности: финансы, здравоохранение, комплаенс;
- Quick Spec: требования сгенерированы автоматически и никем не читаны.

## Дополнительные проверки

Идея из `github/spec-kit`: требования — тоже текст, и у него можно проверить **качество**, как у кода.
Полезные категории сверх пяти основных:

| Проверка | Что искать |
|---|---|
| Completeness | требование недоговаривает: не сказано, что при отказе |
| Clarity | формулировка допускает второе прочтение |
| Consistency | два требования описывают одно по-разному |
| Measurability | нет числа, единицы или наблюдаемого факта |
| Coverage | заявленная возможность не покрыта ни одним критерием |
| Dependencies | неявная зависимость от другой фичи или сервиса |
| Ambiguities | слова-обёртки: «правильно», «корректно», «оптимально» |

Проверка-чеклист пишется по домену и заполняется по мере ревью. Пункт вида «проверить, что…» в чеклист не
годится — это задача, а не вопрос о качестве текста. Каждый пункт проверяем и имеет ссылку на место в
спеке (`§2.1`), пометку `[Gap]`, `[Ambiguity]`, `[Conflict]` или `[Assumption]` — если место ещё не решено.

Метрики, которые стоит вывести в отчёт: доля требований, покрытых задачами, и число находок по категориям.
Растущее число `[Ambiguity]` — сигнал, что требования пишутся словами вместо чисел.
