# Спек-режим

Протокол: идея → `requirements.md` → `design.md` → `tasks.md` → исполнение по волнам.
Механика воспроизведена с Kiro (AWS): артефакты лежат там же, где читал бы их Kiro, — спека остаётся совместимой.

## Что создаётся

Каталог `.kiro/specs/<feature>/`, имя фичи — **kebab-case** (`user-authentication`, не `UserAuthentication`).

| Файл | Содержимое |
|---|---|
| `requirements.md` **или** `bugfix.md` | требования в EARS / анализ бага |
| `design.md` | архитектура, диаграммы Mermaid, интерфейсы, модели данных, обработка ошибок, стратегия тестирования |
| `tasks.md` | дискретные задачи с чекбоксами и ссылками на требования |
| `spec.json` | состояние: режим, workflow, фаза, гейты (см. `references/spec-protocol.md`) |

Каталог настраивается: `SPEC_DIR` (по умолчанию `.kiro/specs`). Оставь `.kiro/specs` — тогда ту же спеку
откроет IDE Kiro, и наоборот.

## Три фазы, два гейта

```
идея → [Фаза 1: требования] --гейт--> [Фаза 2: дизайн] --гейт--> [Фаза 3: задачи] → исполнение
```

Гейт — это **явное одобрение человеком**, не молчание. Дословные вопросы гейта (как в Kiro):

| Фаза | Вопрос |
|---|---|
| Requirements | «Do the requirements look good? If so, we can move on to the design.» |
| Design | «Does the design look good? If so, we can move on to the implementation plan.» |
| Tasks | «Do the tasks look good?» |

Одобрением считается только явное «да / approved / looks good». Молчание, «ок, посмотрю» или смена темы —
**не** одобрение. После каждой правки гейт спрашивается заново.

## Выбор режима

| Режим | Когда | Порядок фаз |
|---|---|---|
| **Feature — Requirements-First** (по умолчанию) | поведение системы известно, архитектура свободна, фича от потребности | требования → дизайн → задачи |
| **Feature — Design-First** | архитектура уже есть или жёстко задана; важны NFR (latency, throughput, compliance); проверка осуществимости до объёма работ | дизайн → требования → задачи |
| **Quick Spec** | фича понятная, править требования/дизайн не собираешься; нужна скорость | все три артефакта за один проход, **без гейтов**, но с уточняющими вопросами вперёд |
| **Bugfix Spec** | баг в критическом пути, прошлые фиксы давали регрессии, root cause неочевиден | `bugfix.md` → дизайн → задачи |

Workflow **не переключается** после старта: выбрал Requirements-First — это на всю спеку. Нужен другой —
заводится новая спека, контент переносится копированием. Два workflow в одном проекте — норма (Design-First
для проверки осуществимости, потом Requirements-First для полной разработки).

Выбор режима записывается в `spec.json`. Второй раз не спрашивать.

## Жёсткие правила

Нарушение любого из них ломает режим — это не рекомендации.

**Требования**

- Первая версия `requirements.md` пишется **из сырой идеи, без серии уточняющих вопросов**. Точечный вопрос —
  можно, допрос в пять шагов — нет.
- Код в этой фазе **не исследуется**.
- Каждое требование — `### Requirement N: <область>`, ID **только числовой** (`Requirement A` запрещено).
- Критерии приёмки — нумерованный список в EARS, минимум один на требование.
- Никаких технологий и имён фреймворков в требованиях: это дизайн. Грамматика — `references/ears.md`.

**Дизайн**

- Отдельные research-файлы **не создаются**: исследование идёт контекстом в `design.md`.
- `design.md` покрывает **все** требования; у каждого требования есть компонент, контракт или поток.
- Диаграммы — Mermaid. Пустых секций и `TBD` не остаётся.
- Нашли пробел в требованиях — возвращаемся к требованиям, а не затыкаем дыру в дизайне.

**Задачи**

- Заголовок ровно `# Implementation Plan`, максимум **два уровня** (`1.`, `1.1`, без `1.1.1`).
- Только задачи, выполнимые написанием, правкой или тестированием кода. Запрещены: деплой, документация,
  обучение пользователей, сбор фидбэка, маркетинг, орг-изменения, ручной прогон приложения.
- Каждая задача заканчивается секцией деталей со ссылкой `_Requirements: 1.1, 2.3_` на **гранулярные**
  подтребования, не на user story.
- Задача без ссылки на требование — мусор. Требование без задачи — дыра, возврат к дизайну.
- Все задачи вместе **соединяют** компоненты: висящего кода, не подключённого на предыдущем шаге, не остаётся.
- Формат, зависимости и волны — `references/tasks-and-waves.md`.

## Гейт ревью перед записью файла

Перед записью каждого артефакта — ревью **черновика**, с механическими проверками первыми:

1. **Числовые ID** есть у каждого требования.
2. **Критерии приёмки** есть у каждого требования.
3. **Нет языка реализации** в требованиях (имена БД, фреймворков, паттернов API).
4. Для дизайна: **traceability** — все ID из `requirements.md` встречаются в `design.md`; File Structure Plan
   содержит реальные пути, не `TBD`; у каждого компонента есть файл.
5. Для задач: **покрытие** — каждый ID требований в хотя бы одной задаче; каждая подзадача проверяема и
   укладывается в 1–3 часа.

Локальные дефекты — правим и проверяем заново. Цикл ограничен **двумя** проходами; дальше — не затыкать
дыру, а поднять проблему человеку: требования или дизайн неоднозначны.

## Анализ требований (Analyze Requirements)

Запускается после генерации требований, особенно для quick-спеки и сложных фич. Ищет **поперёк всего набора**,
а не построчно, пять категорий:

1. **Logical inconsistencies** — по отдельности осмысленны, вместе невыполнимы.
2. **Ambiguities** — «большие файлы», «быстрый ответ» → разные реализации у разных исполнителей.
3. **Conflicting constraints** — функциональные и нефункциональные требования, которые не уживаются.
4. **Unstated assumptions** — ссылки на неопределённые концепции.
5. **Missing edge cases** — отказы, границы, конкурентный доступ.

Анализ занимает минуты: он рассуждает по всему множеству. Каждая находка — требования-участники, объяснение
простым языком, варианты исправления. Ответы обновляют `requirements.md`. Подробности, формат отчёта и
дополнительные проверки из spec-kit — `references/analyze-requirements.md`.

## Исполнение задач

- Перед задачей читаются `requirements.md`, `design.md` **и** `tasks.md`.
- **Одна задача за раз.** Подзадачи — до родительской.
- Статус обновляется сразу по ходу: `- [ ]` → `- [x]` (готово), `- [F]` (не вышло, с причиной).
- После завершения запрошенного объёма — **стоп** и отчёт. К следующей задаче без запроса не переходить.
- Верификация — против требований, указанных в задаче, а не «выглядит нормально».

**Волны.** Задача N зависит от всех предыдущих — порядок и есть основная зависимость. Независимые задачи
помечаются ` (P)` и группируются в волны: основание → ядро → интеграция → валидация. Волны идут
последовательно, задачи внутри волны — параллельно. Полные правила и маркер `_Depends:_` —
`references/tasks-and-waves.md`.

Массовый прогон берёт только **обязательные** невыполненные задачи; опциональные (`- [ ]*`) пропускает.

**Гейт перед `[x]`.** Отметка «готово» — это утверждение, и оно проверяется, а не заявляется. Перед переводом
задачи в `- [x]` прогони `jev_gate` (тул jev MCP, порядок работы — скилл `jev-ops`): `request` — задача с её
`_Requirements:_`, `diff` — `git diff` по правке, `claims` — что именно заявляешь («тесты прошли»,
«Requirement 3 покрыт»), `evidence` — `{ text: <вывод прогона>, tests: <команда и её вывод> }`.
`auto` — можно отмечать; `review`/`escalate` — сначала разобраться, что не сошлось (`test_gap` — нет теста
на заявленное, `spec_match` — правка мимо требования). Гейт не заменяет прогон: тесты запускаешь ты,
`jev_gate` только читает evidence.

## Корректность (property-based тесты)

Дизайн извлекает из EARS-требований **свойства**: «для любых входов, где держится предусловие, верно …».
Типовые формы — инвариант, round trip, идемпотентность. Для багфикса — четыре: условие бага `C`,
постусловие `P`, свойство фикса (`C ⇒ P`), свойство сохранности (`¬C ⇒ поведение не изменилось`).
PBT — **свидетельство, не доказательство**; к ним прилагаются обычные тесты. Детали —
`references/correctness.md`.

## Постоянный контекст (steering)

`.kiro/steering/{product,tech,structure}.md` — память проекта: назначение, стек и конвенции, организация кода.
Дизайн и задачи не повторяют её, а опираются. Документировать нужно паттерны, не перечень файлов:
«если новый код следует существующим паттернам, steering обновлять не нужно». Остальное — `references/steering.md`.

## Команды

| Команда | Что делает |
|---|---|
| `/spec <аргумент>` | диспетчер: `new`, `run`, `analyze`, `status`, `verify` или имя спеки |
| `/spec-new` | новая спека: режим и workflow |
| `/spec-quick` | все три артефакта за один проход без гейтов |
| `/spec-bugfix` | `bugfix.md` и фикс без регрессий |
| `/spec-analyze` | анализ требований поперёк набора |
| `/spec-tasks` | задачи: сгенерировать, синхронизировать с реализацией, выполнить волнами |

Из `github/spec-kit` добавлены идеи, которых у Kiro нет: **constitution** (принципы проекта как проверяемый
инвариант), **clarify** (до 5 точечных вопросов по таксономии), **checklist** (проверка качества самих
требований), **converge** (append-only сверка кода со спекой). Раздел «Улучшения из spec-kit» в
`references/spec-kit.md`.

## Отличие от Kiro

Одно сознательное: Kiro скрывает от пользователя, на какой он фазе («Do not tell the user about this
workflow»). Здесь фаза называется явно — это инструмент, а не магия, и человеку нужно понимать, где он стоит.
