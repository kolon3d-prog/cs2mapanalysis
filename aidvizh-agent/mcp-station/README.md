# mcp-station

Станция поставки MCP: одна команда ставит серверы из каталога в конфиги клиентов — omp/pi и opencode.
Без абсолютных путей, без секретов в репозитории, с Windows-обёрткой.

## Клиенты

| клиент | где лежит конфиг | формат записи |
|---|---|---|
| `omp` (он же pi-форк `oh-my-pi`) | `~/.omp/agent/mcp.json` (`$PI_CODING_AGENT_DIR/mcp.json`) | `mcpServers`: stdio — `command`+`args`, http — `type: http` + `url` + `headers` |
| `opencode` | `~/.config/opencode/opencode.json` (`$XDG_CONFIG_HOME`) | `mcp`: собственная запись клиента рядом с его примером (ниже); пытаться уложить три клиента в одну схему — запрещено |
| `pi` | `~/.pi/agent/mcp.json` (`$PI_CODING_AGENT_DIR/mcp.json`) | `mcpServers`: stdio — `command`+`args`, http — `url` + `headers` (без `type`) |

**У самого pi MCP нет** — его даёт расширение `pi-mcp-adapter`, которое и читает этот файл:

    npm install -g --ignore-scripts @earendil-works/pi-coding-agent@0.87.1
    pi install npm:pi-mcp-adapter

Путь и формат взяты не из README, а из самого адаптера: `getPiGlobalConfigPath()` возвращает
`<agent dir>/mcp.json`, а `loadMcpConfig()` разбирает наши записи (это проверяется тестом — если
адаптер установлен, набор читает наш файл его же парсером).

## В один клик

    bin/mcp-station.sh              # linux/macOS/git-bash: core-серверы каталога в оба клиента

На Windows — либо то же из PowerShell, либо двойной щелчок по `bin/mcp-station.cmd`:

    pwsh -File bin/mcp-station.ps1
    pwsh -File bin/mcp-station.ps1 list
    pwsh -File bin/mcp-station.ps1 install exa -WhatIf
    pwsh -File bin/mcp-station.ps1 install --profile keyed

Без аргументов станция ставит **только core** — серверы, которым ключ не нужен. Серверы с ключом
(`keyed`) ставятся явно: `--profile keyed`, `--profile all` или по имени (`install exa`). Что
произойдёт: в `~/.omp/agent/mcp.json` допишутся записи `mcpServers`, в
`~/.config/opencode/opencode.json` — `mcp`. Чужие ключи в этих файлах не трогаются, перед записью
кладётся `.bak`, повторный запуск ничего не меняет. После установки станция помнит, что и с каким
отпечатком она поставила (`outdated` и `update` работают по этому состоянию).

## Команды

    mcp-station                     поставить core-серверы каталога
    mcp-station install [имена...]  поставить выбранные серверы (--profile keyed|all — целиком)
    mcp-station update [имена...]   привести конфиги к каталогу: переписать изменившееся, добавить
                                    недостающее, с --prune снять то, чего в каталоге больше нет
    mcp-station outdated            что устарело: каталог против состояния станции и конфигов
    mcp-station rollback            вернуть конфиги и состояние к предыдущему снимку
    mcp-station remove [имена...]   снять серверы
    mcp-station list                что есть в каталоге
    mcp-station status              что стоит в клиентах: тир и свежесть
    mcp-station check [имена...]    проверить файлы, переменные и доступность команд
    mcp-station verify [имена...]   живая проверка: поднять сервер по записи из конфига клиента и
                                    сделать рукопожатие MCP (initialize → tools/list)

флаги: `--client omp|pi|opencode|all` (по умолчанию all), `--profile core|keyed|all` (по умолчанию
core), `--dry-run`, `--prune`, `--yes`, `--json`, `--secrets-file <путь>`,
`--opencode-headers literal|env`, `--pool`, а для `verify` ещё `--timeout <сек>` (по умолчанию 20)
и `--exclude <имена через запятую>`.

## Тиры, состояние и обновление

Каждая запись каталога помечена тиром, и тир выводится из ключей: `core` — ключ не нужен, `keyed` —
нужен. Расхождение станция считает ошибкой каталога и говорит вслух (тест это проверяет): новый
сервер с ключом не может незаметно уехать в базовый набор.

    core   basic-memory, bpftrace, camoufox, chrome-devtools, frida-mcp, gdb, inspo, lldb,
           mitmproxy-mcp, playwright, radare2, skills-hub, stealth-browser, wiki, wireshark-mcp
    keyed  exa, firecrawl, jev, lazyweb, serper, tavily

Состояние станции живёт в рантайме — `~/.local/state/mcp-station/installed.json` (не в репозитории и
не в конфигах клиентов): схема, `catalog_hash`, время, по каждому серверу — тир, спецификация записи
и **отпечаток** (sha256 от нормализованного содержимого `argv`/`url`/`headers`) для каждого клиента,
плюс последние пять снимков конфигов для отката. Значения ключей в отпечаток не входят: у заголовка
остаются имя переменной и формат (`Bearer %s`), поэтому смена ключа не выглядит как «каталог
изменился», а смена `argv`/`url`/формата — выглядит (semver для этого не нужен).

    bin/mcp-station.sh outdated           # что устарело: таблица по трём сторонам
    bin/mcp-station.sh outdated --json    # то же машинно: status current|changed|missing|orphan|foreign|unknown

`outdated` сверяет три стороны: каталог (желаемое), `installed.json` (что ставила станция) и факт в
конфигах клиентов. Статусы: `current` — всё сходится; `changed` — каталог или отпечаток разошёлся;
`missing` — в каталоге есть, у клиента нет; `orphan` — стоит, но в каталоге его больше нет (а запись
наша); `foreign` — стоит, а ставила не станция: например `camoufox`, которого прописал установщик
проекта абсолютным путём к venv, или ручная запись — такие станция не трогает и только докладывает;
`unknown` — сверка не состоялась: источник не прочитать, и вердикт был бы догадкой. Так помечаются все
серверы, когда не разобрать `installed.json` (станция не знает, что из записей поставила она), и когда
не прочитать каталог — пустой или недоступный (сверять не с чем; у каталога целиком в отчёте своя
строка `(каталог)`, у неразобранного файла — строка его имени). Сводка считает их как `unknown`, `ok`
становится `false`, а в человекочитаемом выводе есть строка «не смог узнать: N — почему»: недоступный
источник — это не «свежо», а честное «не смог узнать». Для дела (`install`, `update`, `check`, `list`,
`status`, `verify`, `remove`) пустой или нечитаемый каталог — отказ с причиной и код 1, а не молчаливое
«готово»; `rollback` каталог не нужен вовсе — это путь восстановления.

    bin/mcp-station.sh update             # обновить поставленное и добавить недостающий core
    bin/mcp-station.sh update --dry-run   # то же, но ничего не писать
    bin/mcp-station.sh update --prune --yes  # заодно снять сирот (без --yes спросит в терминале)

`update` — reconcile без переустановки: переписываются только те наши записи, что разошлись с
каталогом (в отчёте видно, что именно: `argv`, `url`, `заголовок Authorization`, клиент), недостающие
добавляются, уже актуальные не трогаются вовсе (повторный прогон ничего не пишет). Чужое остаётся на
месте и попадает в отчёт. `--prune` снимает **только сирот со своим отпечатком**; `--yes` — «не
спрашивай». Без профиля `update` берёт всё, что уже стоит, плюс недостающий core; `--profile keyed`
или `all` добавляет и серверы с ключом.

    bin/mcp-station.sh rollback           # вернуть предыдущий снимок (файлы и состояние)
    bin/mcp-station.sh rollback --dry-run # показать, что вернётся

Перед каждым изменением конфигов станция кладёт снимок (последние пять; лишние снимки уходят сами) —
именно до записи, поэтому откат возвращает прежнее содержимое, а не только что записанное; рядом с
конфигом остаётся `.bak`. Снимок ложится и на `install`, и на `update`, и на `remove`. `rollback`
возвращает и файлы, и состояние к снимку; когда снимков нет — честно говорит об этом (код возврата 1).
Ничего, кроме состояния станции и уже имеющихся `.bak`, для отката не нужно.

## Каталог

Один файл на сервер, без секретов и без путей к диску:

```json
{
  "name": "firecrawl",
  "kind": "stdio",
  "tier": "keyed",
  "description": "веб-скрейп, поиск и извлечение через Firecrawl",
  "argv": ["bash", "-lc", "set -a; . \"$MCP_SECRETS\"; set +a; exec npx -y firecrawl-mcp@3.25.4"],
  "requiresEnv": ["FIRECRAWL_API_KEY"],
  "clients": ["omp", "opencode"]
}
```

Готовая запись в нативной схеме opencode — прямо рядом с общим примером: у stdio
состав команды пишется отдельным строковым полем `command` плюс массивом `args`
(порядок строгий — «(command + args) по строкам, слева направо»); у http —
`type: "remote"` + `url` (`environment` вместо `env`):

```json
{
  "firecrawl": {
    "type": "local",
    "command": ["bash", "-lc", "set -a; . \"$HOME/.config/opencode/secrets/env\"; set +a; exec npx -y firecrawl-mcp@3.25.4"]
  }
}
```

- `tier` — `core` (без ключа, ставится по умолчанию) или `keyed` (нужен ключ, ставится явно).
  Тир не свободное поле: сервер с `requiresEnv`/`headers[].env` обязан быть `keyed`, сервер без них —
  `core`, иначе станция отказывается работать с каталогом (и это проверяет тест).
- `approval` (необязательно) — список тулов сервера, которые ставятся под подтверждение: opencode
  получает `permission["<сервер>_<тул>"] = "ask"`, omp — `tools.approval["mcp__<сервер>_<тул>"] = "prompt"`
  (дефисы имени сервера — в подчёркивания). У pi такого механизма нет — гейты туда не пишутся.
  Сейчас так закрыт `skills-hub.skills_install` — установка чужого скилла идёт с полными правами агента.
- `$MCP_SECRETS` — файл с ключами; по умолчанию `~/.config/opencode/secrets/env`, меняется
  `MCP_STATION_SECRETS` или `--secrets-file`. Пути считаются от `$HOME` (в тестах — от `MCP_STATION_HOME`).
- `kind: stdio` → `argv`: у omp/pi — строковое поле `command` плюс массив `args`, у opencode —
  массив `command` (см. пример выше: это нативная запись клиента, а не прятание её в общий `argv`).
- `argvWindows` (необязательно) — тот же состав команды для Windows, без `bash`. Нужен там, где Unix-форма
  идёт через шелл (`bash -lc` с раскрытием `$HOME` или загрузкой ключей из файла): в конфиге Windows шелла
  нет, а `bash` в PATH часто чужая заглушка. `$HOME` и `$STATION` в токенах раскрываются станцией на момент
  установки, разделители приводятся к виндовым. Записи без этого поля на Windows не ставятся — с явной
  строкой, а не молча (настоящий Git Bash спасает: запись встанет с абсолютным путём к нему, см. «Windows»).
  Поле есть у всех stdio-серверов каталога, кроме трёх записей без Windows-рантайма — `bpftrace`, `lldb`,
  `radare2` (почему — в «Платформах отладочных записей»). У остальных: у `npx`-записей
  (`inspo`, `playwright`, `chrome-devtools`) это `cmd.exe /c npx …` — node не запускает `.cmd` напрямую;
  у серверов с ключом —
  обёртка `bin/entryenv.mjs` с настоящей командой после `--` (она докладывает ключи из файла в окружение,
  поэтому в конфиге их нет).
- `envWindows` (необязательно) — окружение записи для Windows: `env` у omp/pi, `environment` у opencode.
  Туда попадает то, что на Unix делает обёртка (у `camoufox` — профиль `CAMOUFOX_CAPS`,
  `research,browser,session,vision`). Значение, уже заданное владельцем в конфиге клиента, не перетирается:
  сузить профиль можно прямо там.
- `kind: http` → `url` + `headers`, где значение заголовка берётся из переменной окружения:
  omp и pi получают на Unix подстановку `!set -a; . "$MCP_SECRETS"; set +a; printf '<формат>' "$VAR"` (ключ
  в конфиг не попадает), opencode — либо значение из файла ключей (`literal`, по умолчанию), либо
  `{env:VAR}` (`--opencode-headers env`, если процесс opencode видит эту переменную). На Windows шелла нет,
  поэтому omp и pi получают значение так же, как opencode; тот же выбор «пусть клиент видит переменную»
  включают `MCP_STATION_OMP_HEADERS=env` и `MCP_STATION_PI_HEADERS=env`.
- `verifyTimeout` (необязательно, секунды) — сколько `verify` ждёт именно этот сервер: нужно тем, кто
  поднимается долго (браузерные). Важнее общего `--timeout`.

добавить свой сервер: положить `catalog/<имя>.json`, проставить тир по ключам и запустить станцию.

## Скилл станции

`skill/jev-ops` — свой скилл про сервер `jev`: когда звать его тулы (screen, verify, gate, find,
rerank, classify, decide, compare, extract), как он у нас подключён (OpenRouter, ключ из файла
ключей, модель `typesafe/jev-1.13`, цена) и какие грабли проверены. Текст живёт только здесь;
коллекция `../skills-station` держит на него ссылку (источник `своё: mcp-station/skill`),
а `skills-station install jev-ops` раскладывает его в слои клиентов. Дизайн вопросов
(Choice/Score/Noul, criteria, confidence) скилл не дублирует — за него отвечает официальный
`typesafe-ai`.

## Серверы с локальной сборкой и рантайм-окружением

Один сервер каталога ставится не через `npx`, а из git: `stealth-browser`
(stealth-browser-mcp на nodriver — браузер против антибот-систем):

    bin/stealth-setup.sh          # git clone + uv venv (python 3.13) + зависимости

Дальше как обычно: `mcp-station install stealth-browser`. Нужны `git` и `uv`
(системный python 3.14 не собирает зависимости — uv сам скачает 3.13).
Пока сервер не собран, клиент получает внятную ошибку, а не молчание:
`stealth-browser не собран: запусти mcp-station/bin/stealth-setup.sh`.

`camoufox` (браузерный ресёрч на анти-детект Firefox, проект camoufox-research) устроен так же, но
окружение собирает **сам проект**, а не эта станция: код лежит в клоне, рантайм — в
`$HOME/.venvs/camoufox-research` (то же имя записи, что пишут установщики проекта —
`scripts/install_mcp.py`, `install.ps1`):

    bash scripts/install.sh          # из клона проекта: зависимости, браузер, venv в рантайме

Дальше `mcp-station install camoufox` — запись ставится во все три клиента и не требует,
чтобы окружение уже было (в конфиг попадает только `$HOME`, абсолютных путей репозитория нет).
Нет окружения — клиент получает подсказку, а не молчание:
`camoufox не установлен: нет окружения в рантайме ($HOME/.venvs/camoufox-research)`, дальше
шаг установки. Запись поднимает сервер с профилем `CAMOUFOX_CAPS`, по умолчанию
`research,browser,session,vision` — ресёрч, чтение страниц, живая вкладка (скролл, клики, формы) и
картинки сразу, чтобы у агента не было «запись есть, а тулов нет». Профиль, заданный снаружи
(`CAMOUFOX_CAPS=...` в окружении клиента или в его конфиге), не перетирается. Сузить профиль —
сказать это явно, например в конфиге клиента:

    "env": {"CAMOUFOX_CAPS": "research,browser"}          # omp / pi / Claude Desktop
    "environment": {"CAMOUFOX_CAPS": "research,browser"}  # opencode

Полный реестр — `all` (дороже по контексту: больше тулов в промпте).

### Отладочные рантаймы

`frida-mcp`, `wireshark-mcp`, `mitmproxy-mcp`, `bpftrace`, `lldb` собираются одним скриптом —
venv'ы в `$HOME/.venvs`, бинарь `bpftrace-mcp-server` из cargo, мост официального LLDB в `$HOME/.local/bin`.
`gdb` (MCP `mcp-gdb@0.1.3`) сборки не требует вовсе: это `npx`, ему нужны только `gdb` и node.

    bin/debug-setup.sh               # идемпотентно: собранное не трогает, системных пакетов не ставит

Чего не хватает из системного, скрипт печатает (`gdb`, `tshark`, `bpftrace`, `lldb`) —
`sudo dnf install gdb wireshark-cli bpftrace lldb`. Дальше как обычно:

    mcp-station install gdb frida-mcp bpftrace wireshark-mcp mitmproxy-mcp lldb

Пока рантайм не собран, клиент получает строку «… не собран: запусти mcp-station/bin/debug-setup.sh»,
а не молчание. Особенности, проверенные делом: у `frida-mcp` пин `mcp<2` (с `mcp 2.x` падает импорт
`mcp.server.fastmcp`); `gdb` — это `mcp-gdb@0.1.3` (17 тулов, signal-slot) через `npx`, ему нужен только
`gdb` в PATH; `bpftrace` — это `bpftrace-mcp-server` (MCPtrace), ему нужна
`bpftrace` в системе и переменная `BPFTRACE_PASSWD` — на машине с sudo без пароля подходит пустая;
`lldb` — не сам бинарь Fedora, а мост `bin/lldb-mcp-bridge.sh`, потому что в Fedora 22.x `lldb-mcp`
поднимает TCP-бэкенд, а не stdio-сервер.

`radare2` (статический реверс, `r2mcp`) — единственная отладочная запись, которую `debug-setup.sh`
не собирает сам: нужен **upstream radare2 6.x** (в Fedora — 5.x, и `r2pm` на ней не собирает r2mcp).
Скрипт это видит и печатает шаги:

    git clone https://github.com/radareorg/radare2 && cd radare2 && sys/install.sh   # ставит в /usr/local
    r2pm -Uci r2mcp

`r2mcp` кладётся в `~/.local/share/radare2/r2pm/pkg`, клиентам он виден через `r2pm -r r2mcp`.
Полный разбор отладочной линии — что проверено живьём, чем и какие кандидаты остались без проверки
(Windows-дампы, форензика памяти, контейнеры) — в `docs/DEBUG-RE-GAPS.md`.

### Платформы отладочных записей

| запись | Linux | macOS | Windows |
|---|---|---|---|
| `gdb` | ✓ `gdb` + node | ✓ `brew install gdb` | ✓ `gdb` из MSYS2/MinGW-w64 + node, рантайм — сам `npx` |
| `frida-mcp` | ✓ | ✓ | ✓ рантайм собирает `bin/debug-setup.ps1` |
| `mitmproxy-mcp` | ✓ | ✓ | ✓ тот же ps1 |
| `wireshark-mcp` | ✓ `tshark` | ✓ `brew install wireshark` | ✓ Wireshark + tshark в PATH; ps1 кладёт `.cmd`-шим с `WIRESHARK_MCP_ALLOWED_DIRS` |
| `bpftrace` | ✓ (eBPF) | — | — |
| `lldb` | ✓ lldb ≥ 22 | ✓ LLVM из brew (у Apple-шного lldb MCP нет) | — (нужен LLVM 23: в 22.x `lldb-mcp` на Windows — не stdio) |
| `radare2` | ✓ upstream r2 ≥ 6 | ✓ `brew install radare2` ≥ 6 | — (r2mcp под Windows не публикуется) |

Рантаймы собирают два близнеца: `bin/debug-setup.sh` (Linux/macOS) и `bin/debug-setup.ps1` (Windows,
ASCII-only — так требует Windows PowerShell 5.1). Обоим нужен `uv`; `ps1` не собирает cargo-часть:
`bpftrace-mcp-server` и мост lldb остаются Unix-ветками по природе инструментов.

Записи `bpftrace`, `lldb` и `radare2` — Unix-only: без настоящего Git Bash станция не ставит их
на Windows (говорит строкой, а не молчит), а с Git Bash запись встанет, но инструмент всё равно
живёт на Unix. Это не «забыли»: eBPF живёт только в ядре Linux; официальный stdio-`lldb-mcp` на
Windows появится с LLVM 23; `r2mcp` под Windows не публикуется. Для Windows своя линия — `mcp-windbg`
(дампы и ядро Windows, ставится отдельно).

## Windows: нативный запуск без bash

Причина всей возни: на чистой Windows `bash` в PATH — заглушка WSL
(`%LOCALAPPDATA%\Microsoft\WindowsApps\bash.exe`). Она печатает «поставь дистрибутив» и **выходит с
нулём**, поэтому «команда есть» и «сервер ответил» там ложь. Правило станции: на Windows ни один её путь
не спавнит `bash` из PATH — либо нативная ветка (`node`, `cmd.exe`, `entryenv.mjs`), либо настоящий
Git Bash, найденный **по абсолютному пути** и проверенный делом (`bash --version` отвечает «GNU bash»;
заглушка WSL — нет; каталог подстановок `WindowsApps` не считается источником bash вовсе).

Что из этого видно в записях конфигов:

- `argvWindows` — состав команды для Windows, без `bash`. Записи без него на Windows не ставятся:
  станция говорит строкой «запись требует bash, а на Windows его нет — дай `argvWindows` в каталоге или
  поставь Git for Windows» и возвращает 1. Поле есть у всех stdio-серверов каталога, кроме трёх
  записей без Windows-рантайма (`bpftrace`, `lldb`, `radare2`): без настоящего Git Bash станция не
  поставит их строкой, а с ним поставит — и запись сама скажет, что инструмента на Windows нет
  (разбор — в «Платформах отладочных записей»).
- `$HOME` и `$STATION` в `argvWindows` раскрываются станцией на момент установки (в конфиге Windows эти
  переменные никто не раскроет), разделители приводятся к виндовым. Переносимость держится
  переустановкой: `mcp-station update`.
- `cmd.exe /c npx …` — нативная форма `npx`-серверов (`inspo`, `playwright`, `chrome-devtools`):
  node ≥ 18.20 не запускает `.cmd`/`.bat` напрямую (`EINVAL`), а `cmd.exe` есть всегда.
- `envWindows` — окружение записи: `env` у omp/pi, `environment` у opencode. Сюда попадает то, что на
  Unix делает обёртка (`camoufox`: профиль `CAMOUFOX_CAPS=research,browser,session,vision`). Значение,
  заданное владельцем в конфиге клиента, не перетирается — сужение профиля не считается расхождением.
- `bin/entryenv.mjs` — обёртка серверов с ключом (`firecrawl`, `jev`, `serper`, `tavily`). Запись
  выглядит так: `["node", "$STATION/bin/entryenv.mjs", "--", "npx", "-y", "firecrawl-mcp@3.25.4"]`. Обёртка
  читает файл ключей целиком и кладёт переменные в окружение (буквальный эквивалент
  `set -a; . "$MCP_SECRETS"; set +a`: значения файла важнее унаследованных), затем запускает команду
  после `--` и отдаёт её код возврата. Файла ключей нет — строка в stderr и код 1: клиент показывает
  причину, а не молчание. Значения секретов не печатаются нигде.
- Ключи http-серверов на Windows берутся из файла ключей, как у opencode: `!`-подстановку, которую
  выполняет шелл, там некому выполнить. Явный выбор «пусть клиент видит переменную» — переменные
  `MCP_STATION_OMP_HEADERS=env`, `MCP_STATION_PI_HEADERS=env`, `MCP_STATION_OPENCODE_HEADERS=env`.
- Пул ключей ставится своим шимом: `cmd.exe /c <…>/mcp-keypool.cmd <сервер>` (файл пишет
  `writePoolShim`), без bash и без Unix-путей.
- `check` и `verify` разбирают PATH и `PATHEXT` сами: `npx` там означает `npx.cmd`. Разделитель берётся
  из самой переменной, а не «по платформе»: из Git Bash тот же PATH приходит через `:` и с путями
  `/c/...`, и разбор по `;` нашёл бы ноль каталогов. Файлы записей проверяются `isAbsolute()`
  (`C:\…`, `\\server\…`, `/…`); `verify` перед запуском записи с `bash` спрашивает настоящий Git Bash —
  без него запись получает `spawn-failed` с причиной, а не мусор заглушки.
- Файла ключей может не быть: `install`/`update` заведёт пустой (права 600) и скажет, чем положить ключ
  (`bin/keys.sh add <сервер>`, на Windows `bin/keys.ps1 add <сервер>`).
- Рядом с конфигом станция держит не больше пяти своих `.bak`; более старые (в том числе ручные копии
  вида `opencode.json.bak-…`) переезжают в рантайм `~/.local/state/mcp-station/dump/`, а не удаляются —
  в отчёте видно, сколько перенесено.
- Обёртки `bin/mcp-station.ps1` и `bin/keys.ps1` переключают консоль в UTF-8 перед вызовом движка:
  иначе Windows PowerShell 5.1 декодирует русский вывод в OEM-кодировке.

**Живой Windows не проверялся.** Ветка прогоняется на Linux (`MCP_STATION_PLATFORM=win32`, PATH и через
`;`, и через `:` как из Git Bash, свой `PATHEXT`, подложенные `npx.cmd`, `cmd.exe` и `bash.exe`-заглушка
в каталоге `WindowsApps`) — это проверяет разбор путей и ветвление, но прогон на настоящей Windows этим
не заменяется.

## Ключи

Один файл на всё — `~/.config/opencode/secrets/env` (переопределяется `MCP_STATION_SECRETS`), права 600,
значения нигде не печатаются. Ключей на провайдера может быть сколько угодно: первый пишется как `VAR`,
следующие — `VAR_2`, `VAR_3`… Добавлять можно в любой момент.

    bin/keys.sh                     интерактивное меню (на Windows — двойной щелчок по bin/keys.cmd)
    bin/keys.sh list                имена переменных и маскированные значения
    bin/keys.sh add exa             добавить ключ (значение спросит скрыто; можно --key ЗНАЧЕНИЕ)
    bin/keys.sh add exa --key ...   без интерактива: удобно для скриптов
    bin/keys.sh import              залить пачкой: строки `VAR=значение` со stdin (или --file ФАЙЛ)
    bin/keys.sh remove exa          снять последний ключ (или --var EXA_API_KEY_2)

`import` берёт столько строк, сколько вставишь: известные переменные раскладываются по серверам,
дубликаты и незнакомые имена попадают в отчёт, значения не печатаются.

Файла ключей может ещё не быть — станция это переживёт, только серверы `keyed` не поставит: без ключа
такой сервер ставить нельзя молча, поэтому `install --profile keyed` (или `install exa`) скажет одной
строкой, что нужно и что повторить:

    exa: нужен ключ EXA_API_KEY — bin/keys.sh add exa, затем повтори mcp-station install exa

Серверы `core` ключей не требуют и ставятся как раньше. Доложи ключи (`bin/keys.sh add exa` или
`bin/keys.sh import`) и повтори команду — она допишет ровно эти записи. Код возврата при пропуске
по ключу — 1, чтобы это было видно скриптам; `--dry-run` всегда возвращает 0.

Уже поставленные записи станция без ключа не перетирает: `update` либо перепишет их, когда ключ
появится, либо (если запись не наша) не тронет и доложит.

Пул и переключение при отказе — у http-серверов. Ставим их через прокси:

    bin/mcp-station.sh install exa lazyweb --pool

Тогда в конфиг клиента попадает не сам http-эндпоинт, а шим `$HOME/.local/bin/mcp-keypool <сервер>`:
он отправляет запросы с первым ключом и, если ключ отбит (401/403/429/5xx) или не доехал, молча берёт
следующий — один полный круг по ключам, после чего клиент получает ошибку как есть. Сработавший ключ
запоминается, так что перебора на каждом запросе нет. Переключения пишутся в stderr сервера (видно в
логах клиента).

Стратегия задаётся `--strategy` или переменной `MCP_STATION_POOL_STRATEGY`:

- `failover` (по умолчанию) — держимся рабочего ключа, меняем только при отказе;
- `round-robin` — ключи идут по кругу на каждый запрос, то есть несколько аккаунтов работают параллельно.

Ключи stdio-серверов (`firecrawl`, `tavily`, `serper`, `jev`) хранить можно сколько угодно, но перебора
у них нет: `npx`-сервер читает ключ на старте, для смены его нужно перезапускать.

Проверить, что пул живой:

    bin/keys.sh list                 # у сервера больше одного ключа
    bin/mcp-station.sh check exa     # файл ключей, переменные, доступность
    # в клиенте — обычный вызов тула этого сервера

## Живая проверка: verify

`check` смотрит файлы, переменные и доступность команд, `outdated` — версии и отпечатки, а `verify`
идёт дальше: он поднимает сервер по записи **из конфига самого клиента** (не «рендер из каталога»:
у omp и pi значение заголовка подставляет `!`-команда — она выполняется, у opencode берётся литерал)
и делает рукопожатие MCP: `initialize` (protocolVersion с перебором разумных версий) → `tools/list`.
Это ответ на вопрос «клиент реально получит рабочее соединение», а не «ключ в конфиге есть».

    bin/mcp-station.sh verify                                  # все записи всех клиентов
    bin/mcp-station.sh verify wiki basic-memory skills-hub     # быстрое подмножество: три сервера
    bin/mcp-station.sh verify --exclude playwright,chrome-devtools,stealth-browser,camoufox
    bin/mcp-station.sh verify --client omp --timeout 60        # один клиент, больше времени
    bin/mcp-station.sh verify --json                           # машинно (прогресс уходит в stderr)

Состояния: `connected` — рукопожатие состоялось (видно имя сервера и число тулов); `no-handshake` —
ответил, но не по протоколу MCP (в stdout мусор, нет `protocolVersion`, отказ на `tools/list`);
`spawn-failed` — не запустился или упал (в ошибке код возврата и первая строка stderr);
`timeout` — не ответил за отведённое время (процесс гасится вместе со своими детьми, сирот не
остаётся); `http-error` — http-запись: сеть, статус (`HTTP 401`), не получить значение заголовка.
Имени нет в конфиге клиента — тоже видно (`spawn-failed`, «записи нет»): поднимать нечего, и молчать
об этом нельзя. Значения ключей и заголовков в вывод не попадают. Каждая запись помечается `ours` —
своя она или чужая: состояние станции помнит отпечатки всего, что ставила, форму записи сверяет каталог.
Код возврата 1 — если не поднялась **наша** запись; чужая (свой сервер покупателя, запись чужого
установщика) называется строкой `чужое, не считаем: <клиент>/<имя> — <состояние>` и провалом дома не
считается. Состояние станции не прочитать — формой не гадаем: своим считаем то, чьё имя есть в каталоге,
и в отчёте стоит `owners: "catalog"`.

В `--json` по каждому клиенту видно `file`, `installed` (что лежит в конфиге) и `servers` (что
проверяли: `name`, `state`, `ms`, `tools`, `server`, `error`, `ours`), а сводка — `total`/`connected`/
`failed` (сумма) плюс `failed_ours` (свои) и `foreign_failed` (чужие); чужие провалы перечислены
отдельным массивом `foreign_failures`.

**Проверка не бесплатна**: она поднимает настоящие серверы, часть из них тянет браузер (`playwright`,
`chrome-devtools`, `stealth-browser`, `camoufox`). Отсюда `--timeout <сек>` (по умолчанию 20 — на
один сервер, а не на весь прогон), `--exclude` и имена для быстрого подмножества. Если сервер не
ответил за пять секунд, в прогрессе видно, почему висит: `пока не ответил — поднимаю браузер, это
долго`. Тяжёлая запись каталога может задать себе своё время полем `verifyTimeout` (секунды) — оно
важнее `--timeout`.

Сколько это стоит на этой машине (ключи на месте, 14 серверов в конфиге каждого клиента):

    verify wiki basic-memory skills-hub      9 проверок     13 с
    verify (весь конфиг, --json)            42 проверки    61 с

Чего `verify` не делает: он не заменяет `check` (там файлы, переменные и команды) и `outdated` (там
версии и отпечатки). Он отвечает только на один вопрос — заработает ли соединение, а «сервер
отвечает» и «запись совпадает с каталогом» — разные вещи.

## Проверка

    bin/mcp-station.sh check            # ok / чего не хватает
    bin/mcp-station.sh status           # что стоит: тир и свежесть (актуально/устарело/чужое)
    bin/mcp-station.sh outdated         # что устарело против каталога (и --json для скриптов)
    bin/mcp-station.sh verify           # живое рукопожатие MCP по записи каждого клиента
    bats tests/station.bats             # 68 тестов: тиры, профили, оба клиента, состояние, outdated
                                        # (changed/missing/orphan/foreign), update и его идемпотентность,
                                        # prune, rollback, check, ключи (в том числе без файла), пул
                                        # с переключением, запись с рантайм-окружением (camoufox),

## Грабли

- **opencode по умолчанию хранит ключи в самом конфиге.** Для http-серверов (`exa`, `lazyweb`)
  станция по умолчанию пишет значение из файла ключей, как было раньше; чтобы ключей в конфиге не было
  вообще, нужен `--opencode-headers env` **и** чтобы процесс opencode видел переменные (проверено:
  сейчас не видит — в его окружении нет ни `EXA_API_KEY`, ни `LAZYWEB_TOKEN`). Без ключа в файле
  серверы `keyed` вообще не ставятся — станция говорит, какой ключ завести.
- **Записи, поставленные не станцией, она не трогает.** Установщик проекта camoufox пишет запись
  абсолютным путём к venv — `outdated` покажет её как `foreign`, `update` доложит и оставит как есть,
  `update --prune` не снимет, и голый `install` (базовый набор) тоже оставит и доложит. Привести такую
  запись к каталогу можно только явной командой с именем сервера: `mcp-station install camoufox` (запись
  перепишется) или `remove` + `install`. Записи, поставленные станцией раньше (до появления состояния),
  узнаются по форме и обновляются `update` как обычно — включая запись, попавшую не в свою форму
  (omp-вид внутри opencode, без `type`): она читается как наша и `update` её чинит, а не объявляет чужой.
- **На Windows станция не ставит записи, которым нужен `bash`.** Там `bash` в PATH часто оказывается
  заглушкой из дистрибутива WSL: на `-lc` она печатает «поставь дистрибутив» и выходит с нулём, поэтому
  клиент получает мёртвый сервер, а `check` молчит зелёным. Такие записи получают строку «запись требует
  bash, а на Windows его нет — дай `argvWindows` в каталоге или поставь Git for Windows» и код 1. Если
  настоящий Git Bash на машине есть, станция ставит запись с АБСОЛЮТНЫМ путём к нему — и никогда с
  `bash` из PATH. Всё остальное (нативные команды, `cmd.exe /c npx`, `entryenv.mjs`, `envWindows`) —
  в разделе «Windows: нативный запуск без bash»; проверить ветку на Linux: `MCP_STATION_PLATFORM=win32`.
- **omp подставляет ключ только через `bash -lc`** — потому что на Unix значение заголовка в конфиге omp
  это shell-строка с префиксом `!`. На Windows шелла нет, поэтому там omp и pi получают значение из файла
  ключей (как opencode), а не подстановкой; вернуть ссылку на переменную можно
  `MCP_STATION_OMP_HEADERS=env` / `MCP_STATION_PI_HEADERS=env` — если процесс клиента эту переменную видит.
- **`npx`-серверы скачиваются при первом запуске клиента** — если сеть недоступна, сервер не поднимется,
  хотя конфиг правильный. Это же видно и в `verify`: первый прогон может быть заметно дольше, а на
  медленной сети сервер упрётся в `--timeout` (тогда ему можно дать больше времени или пропустить
  командой `--exclude`).
- **`verify` поднимает сервер так же, как это сделает клиент**: запись берётся из конфига как есть, и
  `$HOME` внутри неё раскрывается настоящим домашним каталогом (`MCP_STATION_HOME` подменяет только
  пути станции). Проверка платная — она запускает живые серверы, поэтому `--timeout`, `--exclude` и
  имена нужны, чтобы не гонять тяжёлое без нужды.
- Каталог — единственный источник правды: править конфиги руками не нужно, станция приведёт их к
  каталогу (`install` допишет, `update` обновит и доложит, `remove` снимет, `status` покажет расхождение).
