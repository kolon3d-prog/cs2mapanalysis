# pi-plugins-station

Станция сторонних плагинов `pi`: держит каталог проверенных npm-пакетов и ставит их штатной командой
`pi install`. Ничего своего не изобретает — установку, обновление и снятие отдаёт самому `pi`.

Зачем станция, если есть `pi install`: список из десятка пакетов руками не наберёшь дважды. Каталог
хранит, **что** ставится и **зачем**, а `status` отвечает, что из этого реально стоит — включая случай
«объявлено в настройках, а файлов нет», который `pi list` не показывает.

## Что где лежит

Состояние держит `pi`, и станция его не копирует:

| Что | Где |
|---|---|
| объявленные источники | `~/.pi/agent/settings.json`, поле `packages` |
| файлы пакетов | `~/.pi/agent/npm/node_modules/<имя>` |
| версия стоящего | `package.json` внутри пакета |

Каталог станции — `catalog.json`: имя, источник (`npm:<пакет>`), короткое описание. Пакет считается
**стоящим**, только если он и объявлен в `settings.json`, и лежит в `node_modules`. Объявлен без файлов —
отдельное состояние, его видно в `status`.

Агент-каталог pi берётся из `$PI_PLUGINS_STATION_AGENT`, иначе `$PI_AGENT_DIR`, иначе
`$PI_CODING_AGENT_DIR`, иначе `~/.pi/agent`. Путь к `pi` — `$PI_PLUGINS_STATION_PI` или `pi` из PATH.

## Команды

    bin/pi-plugins-station.sh list                      каталог: что есть и что стоит
    bin/pi-plugins-station.sh status [--json]           стоит / объявлен без файлов / нет; чужое в settings
    bin/pi-plugins-station.sh install [имена…|all] [--dry-run]
    bin/pi-plugins-station.sh update  [имена…|all] [--dry-run]
    bin/pi-plugins-station.sh remove  [имена…|all] [--dry-run]
    bin/pi-plugins-station.sh outdated [--json]         сверить стоящие версии с последними в npm
    bin/pi-plugins-station.sh verify [--json]           целостность каталога и состояния pi

`install` пропускает уже стоящие, `update` — нестоящие. Оба возвращают код 1, если `pi` упал.
`outdated` ходит в npm и годится для `center outdated`; `verify` оффлайновый.

`outdated` спрашивает npm по каждому пакету разом, а не по очереди: тринадцать проб подряд — восемь секунд,
они же параллельно — меньше двух. Ответов три: свежо, есть новее и **не смог узнать** — это когда npm нет в
PATH, он упал или реестр молчит дольше 20 секунд (`$PI_PLUGINS_STATION_NPM_TIMEOUT`, мс). «Не смог узнать» —
не «свежо»: строка выглядит как `@llblab/pi-telegram 0.50.1 → ? (не смог узнать)`, а сводка —
`свежих: N, отстали: M, не смог узнать: K, не стоит: J`. Код возврата всегда 0: сверка — ответ, а не
приговор, судит `center`.

Windows — `pwsh -File bin/pi-plugins-station.ps1 install all` или двойной щелчок
`bin/pi-plugins-station.cmd` (показывает каталог). `-WhatIf` = `--dry-run`.

## Почему в каталоге нет pi-opencode-free

Пакет делает то же, что наш `../omp-zen-free`: открывает бесплатные модели OpenCode в pi. Он не патчит
`fetch`, но поднимает **свой** провайдер и ставит свои заголовки клиента (`x-opencode-client`,
`x-opencode-project`, `User-Agent: opencode/0.0.0`). Наш патч работает на уровне `fetch` и видит запросы
любого провайдера к `opencode.ai`, поэтому он переписал бы его `User-Agent` на свой. Два механизма на
одном шлюзе — лишний риск без выигрыша: ключи и переключение уже закрыты нашим расширением. Нужен
безключевой путь — ставится вручную одной командой, станция его не навязывает.

## Проверка

    bin/pi-plugins-station.sh verify       # каталог: name, source npm:, what, без дублей; settings.json разбирается
    bin/pi-plugins-station.sh status       # что стоит, что объявлено без файлов, что лишнее
    bats tests/station.bats                # 16 тестов

тесты подменяют `pi` и `npm` заглушками (у npm — `NPM_STUB_LATEST`, `NPM_STUB_MAP`, `NPM_STUB_FAIL`,
`NPM_STUB_SLEEP`) и агент-каталог (`PI_PLUGINS_STATION_AGENT`, `PI_PLUGINS_STATION_CATALOG`,
`PI_PLUGINS_STATION_PI`) — ни сети, ни настоящих установок.

## Грабли

- **`pi list` показывает только объявленное.** Пакет, объявленный в `settings.json` и потерявший файлы,
  там выглядит установленным. Это и есть состояние «объявлен, файлов нет» в `status`.
- **Станция не ставит сама.** Всё идёт через `pi install|update|remove`: иначе настройки и файлы разъедутся,
  а pi перестанет считать пакет своим.
- **Плагины pi читаются на старте сессии.** После установки нужен новый сеанс.
- **Проектный слой отдельный.** `pi install -l` пишет в `.pi/settings.json` проекта — станция ставит только
  в пользовательский слой, проектный остаётся рукам.
- **Обновление станции — не обновление плагинов.** Каталог правится руками, версии двигает `update`.
