# spec-station

Станция спек-режима: воспроизводит **spec mode** из Kiro (AWS) — превращает идею или баг в требования,
дизайн и задачи в `.kiro/specs/<фича>/` — и ставит его в клиентов двумя поверхностями: **скиллом** и
**слэш-командами**.

Почему отдельная станция, а не папка в `skills-station`: у спек-режима две поверхности вызова. Скилл ставится
в слой скиллов (это умеет `skills-station`), а команды идут в `commands/` каждого клиента — этого не умеет
никто. Держать их порознь значит иметь режим, который то есть, то нет.

## Что воспроизведено

| Режим | Что делает |
|---|---|
| **Feature — Requirements-First** | требования (EARS) → дизайн → задачи, два гейта одобрения |
| **Feature — Design-First** | дизайн → производные требования → задачи; уровни High Level / Low Level |
| **Quick Spec** | все три артефакта за один проход без гейтов, с уточняющими вопросами вперёд |
| **Bugfix Spec** | `bugfix.md` с секцией `SHALL CONTINUE TO`, четыре свойства, фикс без регрессий |
| **Analyze Requirements** | анализ требований поперёк набора: 5 категорий дефектов |

Из `github/spec-kit` добавлено то, чего у Kiro нет: **constitution** (принципы проекта как проверяемый
инвариант), **clarify** (до 5 точечных вопросов), **checklist** (проверка качества самих требований),
**converge** (append-only сверка кода со спекой). Разбор — в `skill/references/spec-kit.md`.

Протокол сверялся с официальной документацией (`kiro.dev/docs/specs/*`) и с эталонным сообществным портом
`gotalab/cc-sdd`; подробности — в разделе «Источники».

## Совместимость с Kiro

Артефакты лежат там же, где читал бы их Kiro: `.kiro/specs/<feature>/{requirements.md|bugfix.md, design.md,
tasks.md}`. Спеку, созданную здесь, откроет IDE Kiro, и наоборот — спека из Kiro читается здесь. Дополнительно
создаётся `spec.json` с режимом, workflow и состоянием гейтов; Kiro его игнорирует.

Сознательное отличие одно: Kiro скрывает от пользователя, на какой он фазе («Do not tell the user about this
workflow»). Здесь фаза называется явно — человеку нужно понимать, где он стоит.

## Состав

```
spec-station/
├── skill/                    источник скилла spec-mode (своё)
│   ├── SKILL.md              протокол целиком
│   ├── references/           10 справочников по режимам и фазам
│   └── templates/            requirements.md, design.md, tasks.md, bugfix.md
├── commands/                 6 слэш-команд для клиентов
├── bin/                      spec-station.sh | .mjs | .ps1 | .cmd
└── tests/station.bats
```

## Команды станции

    bin/spec-station.sh list                    что в станции: режимы, шаблоны, команды
    bin/spec-station.sh install [флаги]         скилл в слой + команды по клиентам
    bin/spec-station.sh remove  [флаги]         снять
    bin/spec-station.sh status  [флаги]         что стоит
    bin/spec-station.sh verify  [--json]        целостность станции

Флаги:

- `--layer all` (по умолчанию) — канонический слой `~/.agents/skills` плюс клиентские слои, у которых есть
  свой каталог: `opencode` (`~/.config/opencode/skills`), `claude` (`~/.claude/skills`), `omp`
  (`~/.omp/agent/skills`), `pi` (`~/.pi/agent/skills`). Один слой можно назвать явно: `--layer global`,
  `--layer project`, `--layer opencode`;
- `--dir <путь>` — свой путь для скилла вместо слоя;
- `--client omp,pi,opencode,claude|all|none` — куда команды; по умолчанию `all`, но только живым клиентам;
- `--force` — заменить существующие skill/command targets; перед заменой создаётся `.bak` (следующие backups получают `.bak.1`, `.bak.2`).
  (чужие каталоги станция не создаёт). Явный список — приказ: каталог будет создан;
- `--mode link` (по умолчанию) — ссылками на станцию; `--mode copy` — независимой копией;
- на Windows, если файловая ссылка запрещена (`EPERM`/`EACCES`), команды автоматически становятся копиями
  с явной пометкой; после обновления источника повтори `install`;
- `--dry-run`, `--json`.

Windows — та же станция без Git Bash: `pwsh -File bin/spec-station.ps1 install` или двойной щелчок
`bin/spec-station.cmd` (показывает состав).

## Слэш-команды

| Команда | Что делает |
|---|---|
| `/spec <аргумент>` | диспетчер: `new`, `run`, `analyze`, `status`, `verify` или имя спеки |
| `/spec-new` | новая спека: режим и workflow, дальше фазы с гейтами |
| `/spec-quick` | все три артефакта за один проход без гейтов |
| `/spec-bugfix` | `bugfix.md`, root cause, фикс без регрессий |
| `/spec-analyze` | анализ требований поперёк набора |
| `/spec-tasks` | задачи: сгенерировать, синхронизировать с кодом, выполнить волнами |

Формат файла команды — `description:` во фронтматтере плюс тело с `$ARGUMENTS`. Это один формат на всех
клиентов: `omp` разбирает фронтматтер и подставляет `$ARGUMENTS`, `$1`, `$@`; `opencode` читает
`commands/*.md`; `claude` — `~/.claude/commands/*.md`. Так одна команда работает везде, без копий текста.

## Куда ставится

| Что | Слои скилла | Каталоги команд |
|---|---|---|
| `omp` | `~/.omp/agent/skills` | `~/.omp/agent/commands` |
| `pi` | `~/.pi/agent/skills` | `~/.pi/agent/prompts` |
| `opencode` | `~/.config/opencode/skills` | `~/.config/opencode/commands` |
| `claude` | `~/.claude/skills` | `~/.claude/commands` |
| канонический | `~/.agents/skills` | — |

У `pi` тот же механизм, что у остальных, называется **шаблонами промптов** и лежит в `prompts/`, а не в
`commands/`: сам `pi` переносит туда старый каталог миграцией при старте (`dist/migrations.js` —
`renameSync(commandsDir, promptsDir)`). Станция пишет сразу в `prompts/`, иначе команды окажутся там,
откуда `pi` их уже перенёс, а `status` покажет ноль. Подстановка аргументов та же — `$ARGUMENTS`, `$1`, `$@`.

Слои делятся на два вида. Канонический (`global`) и проектный (`project`) держат сам скилл: ссылка ведёт на
`skill/` станции. Клиентские — **зеркала** канонического: ссылка ведёт на `~/.agents/skills/spec-mode`, а не
на станцию. Так у скилла один источник, а слой клиента остаётся ярлыком — ровно как разложены остальные
скиллы на этой машине. `status` помечает «(не туда)», если клиентский слой смотрит мимо канонического.

Живым клиентский слой скиллов считается по своему каталогу (`~/.config/opencode/skills` существует), а
живым клиентом для команд — по каталогу клиента (`~/.config/opencode`). Проверки разные намеренно:
установка команд создаёт каталог клиента, и общая проверка заставляла бы `status` считать клиента без слоя
скиллов слоем с пропавшим скиллом.

`$OMP_AGENT_DIR`, `$PI_CODING_AGENT_DIR`, `$XDG_CONFIG_HOME` учитываются. После установки `omp`/`pi` подхватят
скилл и команды на старте сессии, `opencode` — после перезапуска сервиса. До перезапуска `skill://spec-mode`
не разрешается: реестр скиллов сессии снимается на её старте. Команды это учитывают — в них есть фолбэк
на чтение файлов слоя напрямую.

## В коллекцию скиллов

Скилл лежит в коллекции `../skills-station/collection/spec-mode` **ссылкой** на `skill/` этой станции:
вторая копия текста разошлась бы с источником. В `catalog.json` записан источник `своё: spec-station/skill`.
`skills-station verify` проверяет такие скиллы наравне с остальными.

## Проверка

    bin/spec-station.sh verify      # скилл, справочники, шаблоны, команды — на месте и с frontmatter
    bin/spec-station.sh status      # что стоит в слое, какие команды и у кого
    bats tests/station.bats         # 19 тестов: слои и их зеркала, link/copy, клиенты и их каталоги команд,
                                    # replace, remove, status, verify, сканер абсолютных путей, PS-обёртка

тесты подменяют дом, источник и каталог команд (`SPEC_STATION_HOME`, `SPEC_STATION_SOURCE`,
`SPEC_STATION_COMMANDS`, `SPEC_STATION_CWD`) — реальные клиенты не трогаются.

## На каких ОС проверено

| ОС | чем | статус |
|---|---|---|
| Linux | `bin/spec-station.sh` | проверено: 19 тестов, живая установка в три слоя, команды в четырёх клиентах |
| Windows | `bin/spec-station.ps1`, `.cmd` | обёртка запускалась под PowerShell 7 на Linux (list и `-WhatIf`), тест 17 проходит при `pwsh` в PATH; на настоящей Windows не запускалось |
| macOS | `bin/spec-station.sh` | не проверялось (машины нет); GNU-специфики в движке нет — `[INFERENCE]` |

## Грабли

- **Скилл и команды — разные поверхности.** Установлен скилл, а команды нет — режим вызовется только по
  триггеру описания. Это нормально, если `--client none`.
- **Команды не в `~/.agents`.** Канонический каталог агента команд не держит: `omp`/`opencode`/`claude`
  читают `commands/*.md` из своего каталога, `pi` — `prompts/*.md`. Поэтому одного слоя на всех нет.
- **`pi` переименовывает `commands/` в `prompts/` сам.** Написал в `commands` — при следующем старте `pi`
  перенесёт каталог, и станция будет считать команды поставленными там, где их уже нет (`status` покажет
  `0/6`). Станция пишет сразу в `prompts/`.
- **Чужой клиент не создаётся молча.** При `--client all` каталогов `~/.claude` и подобных станция не делает.
  Нужен явно — перечисли в `--client`.
- **`--mode link` живёт, пока живёт диск.** Ссылки на станцию исчезнут вместе с ним; `--mode copy` переживёт,
  но разойдётся с источником при обновлении — тогда переставь копию тем же `install`.
- **`skill://spec-mode` не разрешается до перезапуска сессии.** Реестр скиллов снимается на старте сессии,
  поэтому свежепоставленный скилл виден файлами, но не по внутреннему URI. Команды `/spec*` это учитывают:
  в них указан фолбэк на чтение `~/.agents/skills/spec-mode/` напрямую.
- **`.kiro/specs` — рабочий каталог проекта, а не станции.** Станция только ставит инструмент; спеки создаёт
  агент в проекте. Если спеки уже лежат в другом месте — задай `SPEC_DIR`.
- **`spec.json` — наш.** Kiro его игнорирует, но и не читает состояние гейтов оттуда. Спека, начатая в Kiro
  и продолженная здесь, спросит режим заново.

## Источники протокола

Официальные: `kiro.dev/docs/specs/` и подстраницы (feature-specs, requirements-first, tech-design-first,
bugfix-specs, quick-spec, analyze-requirements, correctness, best-practices, plan), `kiro.dev/docs/steering/`,
`kiro.dev/docs/hooks/`, блоги Kiro про bugfix и property-based testing.

Сообществные, помечены в тексте справочников: `gotalab/cc-sdd` (эталонный порт: EARS-правило, шаблоны,

traceability-ID), `allanninal/claude-code-skills@kiro-skill` (формулировки гейтов, `.kiro/specs/`),
`jasonkneen/kiro` (spec-process-guide), Gist-выписки системного промпта Spec Agent (дословные MUST-правила
фаз и список запрещённых задач).
