---
description: Спек-режим: new | run | analyze | status | verify | <имя спеки>
---

Включи спек-режим: сначала прочитай `skill://spec-mode` и действуй строго по нему.
Справочники по фазам — `skill://spec-mode/references/`, шаблоны артефактов — `skill://spec-mode/templates/`.
Если `skill://spec-mode` не разрешается (реестр скиллов сессии снят до установки) — читай файлы слоя
напрямую: `~/.agents/skills/spec-mode/SKILL.md` и его `references/`, `templates/`.

Аргумент: `$ARGUMENTS`

Разбор аргумента:

- **пусто** — покажи состояние: список каталогов в `.kiro/specs/`, для каждой спеки режим, workflow, фазу и
  число невыполненных задач по её `spec.json` и `tasks.md`. Ничего не создавай.
- **`new <краткая идея>`** — заведи новую спеку. Один раз спроси режим (Feature / Bugfix / Quick) и, для
  Feature, workflow (Requirements-First / Design-First); выбранное запиши в `spec.json` и больше не спрашивай.
  Дальше иди по фазам с гейтами.
- **`run [<имя>] [<номер задачи>] [--required|--sequential]`** — исполнение задач спеки. Массовый прогон
  берёт только обязательные невыполненные задачи и раскладывает их по волнам: независимые (`(P)`) идут
  параллельно, волны — последовательно. После каждой задачи — статус в `tasks.md` и проверка против
  требований, указанных в задаче. Завершив запрошенный объём — стоп и отчёт, дальше без запроса не идти.
- **`analyze [<имя>]`** — анализ требований поперёк всего набора: пять категорий дефектов, находки с
  требованиями-участниками и вариантами исправления. См. `skill://spec-mode/references/analyze-requirements.md`.
- **`status`** — сводка по всем спекам: фаза, гейты, сколько задач осталось, что зависло.
- **`verify [<имя>]`** — сверка реализации со спекой: `missing`, `partial`, `contradicts`, `unrequested`.
  Секция `## Convergence` дописывается в `tasks.md`; находок нет — файл не меняется вовсе.
- **`<имя спеки>`** — продолжение: прочитай `spec.json`, назови текущую фазу и невыполненные задачи и
  продолжи с места. Гейты не пропускай.
- **`<имя спеки> <фаза>`** — начни указанную фазу (`requirements`, `design`, `tasks`, `implementation`).

Жёсткие правила, которые нельзя нарушать: первая версия требований пишется из сырой идеи без серии
уточняющих вопросов; код в фазе требований не исследуется; отдельные research-файлы не создаются; вперёд без
явного одобрения человеком не идти; гейт спрашивается заново после каждой правки; после одобрения задач
режим останавливается, а не начинает кодить сам.
