description: Новая спека: требования (EARS) → дизайн → задачи, с гейтами одобрения
---

Заведи новую Feature Spec. Сначала прочитай `skill://spec-mode` и `skill://spec-mode/references/spec-protocol.md`
— дальше действуй строго по ним. Шаблоны: `skill://spec-mode/templates/`.
Если `skill://spec-mode` не разрешается (реестр скиллов сессии снят до установки) — читай файлы слоя
напрямую: `~/.agents/skills/spec-mode/SKILL.md` и его `references/`, `templates/`.

Идея фичи: `$ARGUMENTS`

Порядок:

1. **Имя фичи.** Придумай короткое, в kebab-case (`user-authentication`) — оно станет именем каталога
   `.kiro/specs/<имя>/`. Больше ни о чём на этом шаге не спрашивай.
2. **Режим и workflow — один раз.** Спроси и запиши в `spec.json`:
   - Requirements-First — поведение системы известно, архитектура свободна (по умолчанию);
   - Design-First — архитектура уже задана или важны нефункциональные ограничения;
   - Quick — понятная фича, гейты не нужны (тогда сразу `/spec-quick`);
   - Bug — это баг (тогда сразу `/spec-bugfix`).
   Выбор не переспрашивай: workflow после старта не меняется, второй раз не спрашивается.
3. **Требования.** Сгенерируй первую версию `requirements.md` из идеи, **без серии уточняющих вопросов**.
   Код в этой фазе не исследуй. Требования — `### Requirement N: <область>` с числовым ID, критерии приёмки —
   нумерованный список в EARS (`skill://spec-mode/references/ears.md`), минимум один на требование.
   Никаких фреймворков, БД и паттернов API — это дизайн.
4. **Ревью требований.** Механические проверки: числовые ID, наличие критериев, отсутствие языка реализации,
   наличие хотя бы одной строки `If`. Затем гейт: «Do the requirements look good? If so, we can move on to the
   design.» Без явного одобрения вперёд не идти. После правок спрашивать заново.
5. **Дизайн.** `design.md` по шаблону: все требования покрыты компонентами и контрактами, диаграммы Mermaid,
   File Structure Plan с реальными путями, обработка ошибок, стратегия тестирования и свойства для
   property-based тестов. Отдельных research-файлов не создавать.
6. **Гейт дизайна:** «Does the design look good? If so, we can move on to the implementation plan.»
7. **Задачи.** `tasks.md` по формату `skill://spec-mode/references/tasks-and-waves.md`: заголовок ровно
   `# Implementation Plan`, максимум два уровня, `_Requirements:_` на гранулярные подтребования, `(P)` с
   `_Boundary:_` для параллельных, `_Depends:_` только для неочевидных связей. Только задачи, выполнимые
   кодом: деплой, документация, обучение, маркетинг, ручной прогон — запрещены.
8. **Гейт задач:** «Do the tasks look good?» После одобрения — **остановись**. Скажи, что задачи можно
   запускать через `/spec run <имя>`. Сам кодить не начинай: этот проход создаёт только артефакты.

Каждый артефакт проходит гейт ревью **до** записи файла: механические проверки первыми, локальные дефекты —
правка и повторная проверка, не больше двух проходов; дальше поднимай проблему человеку, а не затыкай дыру.
