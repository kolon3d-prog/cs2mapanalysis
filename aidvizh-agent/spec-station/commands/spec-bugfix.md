Bugfix Spec. Сначала прочитай `skill://spec-mode` и `skill://spec-mode/references/bugfix-spec.md`.
Шаблон — `skill://spec-mode/templates/bugfix.md`.
Если `skill://spec-mode` не разрешается (реестр скиллов сессии снят до установки) — читай файлы слоя
напрямую: `~/.agents/skills/spec-mode/SKILL.md` и его `references/`, `templates/`.

Описание бага: `$ARGUMENTS`

1. **Дособери описание.** Нужны четыре части, без них анализ будет гаданием: шаги воспроизведения,
   текущее поведение (дефект), ожидаемое поведение, ограничения — что **не** должно измениться. Чего нет в
   аргументе, о том спроси точечно, одним блоком.

2. **`bugfix.md` — три секции:**
   - `## Current Behavior (Defect)` — **без `SHALL`**: `WHEN <условие>` / `THEN the system <ошибочное поведение>`.
     Дефект — констатация, иначе он неотличим от требования.
   - `## Expected Behavior (Correct)` — с `SHALL`, обычные критерии приёмки в EARS.
   - `## Unchanged Behavior (Regression Prevention)` — дословно `SHALL CONTINUE TO`. Секция не может быть
     пустой: пустая означает, что рядом с багом нет работающего поведения или о нём не подумали. Каждая
     строка проверяема — «работает как раньше» не свойство.
   Запиши `mode: bugfix` в `spec.json`. `requirements.md` не создавай — его заменяет `bugfix.md`.

3. **Анализ.** Найди root cause в коде, а не место проявления. Сформулируй:
   - условие бага `C` — предикат над входом, отделяющий сломанные входы от рабочих;
   - постусловие `P` — что значит «исправлено», наблюдаемо;
   - свойство фикса `C ⇒ P` и свойство сохранности `¬C ⇒ поведение не изменилось`.
   Покажи `C`, `P` и гипотезу root cause человеку до написания кода: это самая дешёвая точка, где
   обнаруживается, что чинится не тот баг.

4. **`design.md`** — root cause analysis, proposed fix approach, три группы свойств для проверки
   (баг существует / фикс работает / сохранность не нарушена).

5. **`tasks.md` — ровно три задачи в жёстком порядке:**
   1. bug-condition тесты — падают на нефиксированном коде;
   2. preservation-тесты — прогон **нефиксированного** кода на входах вне `C`, запись фактического поведения,
      ассерты; на нефиксированном коде проходят, он и есть эталон сохранности. Без этого шага «регрессий нет»
      проверять нечем;
   3. патч.
   После патча обе группы перепрогоняются: bug-condition краснеет → зеленеет, preservation остаётся зелёной.
   Bug-condition не позеленел — гипотеза о root cause неверна, возврат к исследованию, а не «дожать патч».
   Preservation сломалась — у фикса побочные эффекты, патч сужается.

6. **Границы.** Bugfix Spec не превращается в Feature Spec: если root cause показал, что нужна новая
   функциональность, она уходит в отдельную спеку. Для опечатки, простой логической ошибки или однострочной
   правки с понятной причиной весь этот режим не нужен — скажи об этом прямо и предложи обычный фикс.
