# Feature Spec: Requirements-First и Design-First

Два workflow одной и той же Feature Spec. Разница только в том, что первично: поведение или архитектура.

| | Requirements-First | Design-First |
|---|---|---|
| С чего начинается | поведение системы, записанное требованиями | технический дизайн, архитектура или псевдокод |
| Что генерируется из чего | дизайн из требований | требования из дизайна |
| Для чего лучше | продуктовая разработка | технически стеснённые и design-driven проекты |
| Что гарантирует | желаемое поведение описано | техническая осуществимость |
| Гибкость | реализация подстраивается | требования подстраиваются |

Workflow выбирается **один раз при создании** спеки и не меняется. Нужен другой — новая спека.

## Requirements-First

Порядок: **Requirements → Design → Tasks**.

### Шаг 1. Требования

Из сырой идеи генерируется `requirements.md`. Внутри:

- user stories с критериями приёмки;
- системное поведение в EARS (`When … the system shall …`);
- функциональные требования;
- границы и обработка ошибок.

Роль человека на этом шаге: проверить полноту, добавить сценарии, уточнить формулировки. Не «написать
требования» — их пишет режим, человек проверяет.

**Гейт:** «Do the requirements look good? If so, we can move on to the design.»

Опционально сразу после генерации — анализ требований (`references/analyze-requirements.md`).

### Шаг 2. Дизайн

`design.md` покрывает **все** требования:

- архитектура и компоненты, границы модулей;
- sequence-диаграммы и потоки данных (Mermaid);
- модели данных и интерфейсы (контракты);
- обоснование выбора стека;
- обработка ошибок;
- стратегия тестирования, включая свойства для property-based тестов.

**Гейт:** «Does the design look good? If so, we can move on to the implementation plan.»

### Шаг 3. Задачи

Дискретные отслеживаемые задачи: понятные описания, ожидаемый результат, зависимости между задачами,
обязательные и опциональные. Формат — `references/tasks-and-waves.md`.

**Гейт:** «Do the tasks look good?»

### Шаг 4. Исполнение

Задачи по одной или волнами. Это отдельный проход, а не продолжение генерации.

## Design-First

Порядок: **Design → Requirements → Tasks**. Гейты те же, но в обратном порядке.

### Шаг 1. Уровень детализации

Выбирается до начала:

| Уровень | Что содержит | Кому |
|---|---|---|
| **High Level Design** | системная диаграмма, описания компонентов и их взаимодействий, технический подход и паттерны, нефункциональные свойства (performance, scalability, security) | сложные системы, командная работа, документация |
| **Low Level Design** | псевдокод алгоритмов, определения интерфейсов и контрактов, ключевые структуры данных, нефункциональные свойства | быстрый прототип, проверка осуществимости, solo-работа |

### Шаг 2. Дизайн

`design.md` в выбранной детализации. По умолчанию открывается на просмотр, правки — отдельным действием.

### Шаг 3. Требования

Требования **выводятся из валидированной архитектуры** — они гарантированно осуществимы. Записываются теми
же правилами: `### Requirement N`, EARS-критерии, числовые ID.

### Шаг 4. Задачи

Идентичны Requirements-First.

## Импорт существующего

**Есть архитектура или дизайн** → Design-First:

- скормить диаграмму (PNG/JPG), текст или фото доски;
- формализовать в `design.md`;
- вывести требования из архитектуры.

**Есть требования** (`foo-prfaq.md`, PRD, выгрузка из JIRA/Confluence) → Requirements-First:

- положить файл в репозиторий;
- `#foo-prfaq.md сгенерируй спеку из этого`;
- режим читает файл и строит требования и дизайн.

**Есть интеграция с MCP** у JIRA/Confluence/дизайн-инструмента — импорт идёт прямо из него, без файла.

## Когда какой workflow

Requirements-First, если:

- известно **поведение** системы, которое нужно получить;
- архитектура свободна и может быть подстроена под требования;
- фича идёт от потребности пользователя;
- технических ограничений на старте нет.

Design-First, если:

- архитектура или дизайн уже есть;
- система обязана уложиться в жёсткие NFR: latency, throughput, compliance;
- прототипируется конкретный стек;
- нужно проверить осуществимость до того, как обязаться по объёму.

Оба в одном проекте — норма: Design-First для проверки осуществимости, затем Requirements-First для полной
разработки фичи.

## Основной принцип

Опираемся на то, что человек **устанавливает истину по ходу**: пока документ не одобрен, вперёд не идём.
Это не бюрократия — гейт существует ровно потому, что расхождение, найденное на фазе требований, стоит
минуты, а найденное в коде после реализации — часы.
