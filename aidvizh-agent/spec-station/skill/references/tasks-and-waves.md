# Задачи, зависимости, волны

`tasks.md` — последний артефакт спеки и вход в исполнение.

## Формат файла

Заголовок ровно `# Implementation Plan`. Дальше — нумерованный список с чекбоксами, **максимум два уровня**.

```md
# Implementation Plan

- [ ] 1. Set up project structure and core interfaces
  - Create directory structure for models, services, repositories, and API components
  - Define interfaces that establish system boundaries
  - _Requirements: 1.1_

- [ ] 2. Implement data models and validation
- [ ] 2.1 (P) Create core data model interfaces and types
  - Write interfaces for all data models
  - Implement validation functions for data integrity
  - _Requirements: 2.1, 3.3, 1.2_
  - _Boundary: UserModel, OrderModel_

- [ ] 2.2 (P) Implement User model with validation
  - Write User class with validation methods
  - Create unit tests for User model validation
  - _Requirements: 1.2_
  - _Boundary: UserModel_
```

Правила:

- `# Implementation Plan` — дословно этот заголовок.
- Уровни только `1.` и `1.1`. Третий уровень запрещён. Задача-контейнер без собственных деталей — только
  заголовок, без дублирующих пунктов.
- Если у родителя оказался один дочерний пункт — структура схлопывается: `1.1` становится `1.`.
- Нумерация: старшие задачи растут подряд (`1, 2, 3`), младшие сбрасываются внутри старшей (`1.1, 1.2`, затем
  `2.1, 2.2`).
- Детали — подпункты под задачей. Нужны, только если задача не исчерпывается заголовком.
- Ссылка на требования — курсивом, последней строкой деталей: `_Requirements: 2.1, 3.3, 1.2_`. Только ID,
  без описаний и скобок.
- `_Boundary: <компоненты>_` — обязательно для задач с `(P)`: какие модули из дизайна задача трогает. Это же
  и есть проверка, что параллельные задачи не пересекаются.
- `_Depends: 1.2, 2.3_` — только для неочевидных зависимостей между разными группами. Если задача зависит
  от непосредственно предыдущей, порядок это уже выражает, и `_Depends_` не пишется.
- Тестовая задача, которую можно отложить, помечается `- [ ]*`, и в деталях указывается, к какому критерию
  приёмки она относится. Опциональными бывают **только** тесты; реализация и интеграция — никогда.

## Статусы

| Метка | Значение |
|---|---|
| `- [ ]` | не начато |
| `- [ ]*` | не начато, опционально (массовый прогон пропускает) |
| `- [x]` | готово |
| `- [F]` | попытка не удалась; в деталях — причина |

Статус обновляется **по ходу**, а не пачкой в конце: задача помечается выполненной сразу, как проверена.

## Содержание задач

Что описывать: функциональность, бизнес-логику, поведение, доменные понятия, связи данных.

Чего не тащить: пути к файлам, имена функций и сигнатуры, определения типов, имена классов, контракты API,
конкретные структуры данных. Всё это живёт в `design.md`; задача описывает **работу**, а не повторяет контракт.

**Запрещённые задачи** — в `tasks.md` их быть не должно:

- приёмка пользователем или сбор фидбэка;
- деплой в production или staging;
- сбор и анализ метрик производительности;
- ручной прогон приложения для проверки (автоматические end-to-end тесты писать можно);
- обучение пользователей и написание документации;
- организационные и процессные изменения;
- маркетинг и коммуникации;
- любая задача, которую нельзя выполнить написанием, правкой или тестированием кода.

## Порядок фаз — основная зависимость

**Задача N зависит от всех задач перед ней.** Это главный механизм, а не побочный эффект: он и есть ответ на
вопрос «что от чего зависит» в большинстве случаев.

Порядок фаз:

1. **Foundation** — окружение, тестовая инфраструктура, общие утилиты, схема БД, конфигурация.
2. **Core** — основная реализация фичи. Здесь живут параллельные задачи.
3. **Integration** — соединение компонентов, связи через границы.
4. **Validation** — end-to-end тесты, границы, проверки на регрессии.

Foundation почти никогда не содержит `(P)`: он создаёт общие предпосылки. Основание готово — Core становится
главным кандидатом на параллельность.

## Параллельность: маркер `(P)`

`(P)` означает: задача не зависит от непосредственно предшествующих соседей и может идти с ними одновременно.

Ставить `(P)` только если выполнено **всё**:

1. нет зависимости по данным от незавершённых задач;
2. нет общих файлов и общих изменяемых ресурсов;
3. не требуется предварительное ревью или одобрение другой задачи;
4. работа основания, нужная этой задаче, уже сделана более ранними задачами;
5. `_Boundary:_` подтверждает, что области компонентов не пересекаются.

Проверка перед пометкой:

- запуск параллельно не создаст конфликтов при слиянии и выкладке;
- `_Boundary:_` не пересекаются;
- задача проверяема независимо от соседей;
- если осталась зависимость от другой группы — добавлен `_Depends: X.X_`.

Любая непройденная проверка — `(P)` **не ставится**, а причина пишется в деталях задачи. Две похожие задачи
без общей границы всё равно не параллельны, если трогают один модуль.

Маркер ставится сразу после номера, вне чекбокса: `- [ ] 2.1 (P) Build background worker`.

Режим `--sequential` — маркеры `(P)` не ставятся вовсе, задачи идут строго по порядку.

## Волны

Задачи образуют граф зависимостей и раскладываются по волнам:

- **Волна 1** — все задачи без зависимостей. Идут одновременно.
- **Волна 2** — задачи, чьи зависимости закрыла волна 1. Идут одновременно.
- **Волна N** — пока задачи не кончатся.

Волны выполняются **последовательно**, задачи внутри волны — **параллельно**.

```
волна 1:  1, 2.1(P), 2.2(P)          ← одновременно
волна 2:  3.1, 3.2(P), 3.3(P)
волна 3:  4.1  (Depends: 3.1, 3.2)
```

На практике волна вычисляется так: задача попадает в волну `1 + max(волна её зависимостей)` по явным
`_Depends:_` и по неявной зависимости от всех предыдущих обязательных задач. Пометка `(P)` снимает неявную
зависимость от **непосредственных соседей**, но не от более ранних задач и не от `_Depends:_`.

## Гейт ревью перед записью

Прогон по черновику, механические проверки первыми:

**Покрытие**

- каждый ID из `requirements.md` встречается хотя бы в одной задаче;
- каждый компонент, контракт, точка интеграции, runtime-предпосылка и проверка из `design.md` представлены
  хотя бы одной задачей;
- покрытие отсутствует из-за неполного черновика — дополнить и проверить снова;
- покрытие не добавляется, потому что требования или дизайн неоднозначны — **вернуться в ту фазу**, а не
  заделывать дыру в `tasks.md`.

**Исполнимость**

- каждая подзадача выполнима как написана, обычно за 1–3 часа;
- каждая даёт проверяемый результат: поведение, артефакт, эндпоинт, состояние UI, конфигурация, миграция,
  результат интеграции, тест;
- задача, объединяющая независимо проверяемые результаты, делится;
- задача, которая слишком мелкая или состоит из учёта, схлопывается;
- неявные предпосылки вынесены в предшествующие задачи;
- после правок `_Depends:_`, `_Boundary:_` и `(P)` перепроверены — утверждение о параллельности должно
  соответствовать текущему графу.

**Границы цикла:** не больше двух проходов правка-проверка, дальше — поднимать реальный пробел, а не крутиться.

## Синхронизация с кодом

Работа шла в другом сеансе и часть задач уже сделана:

- **Sync Files** — сверка чекбоксов с фактической реализацией, выполненные отмечаются сами;
- либо «Check which tasks are already complete» — режим просматривает код и отмечает.

Требование без задачи — сигнал, что между дизайном и задачами потерялась работа. Задача без требования —
её стоит удалить или связать с реальным требованием.
