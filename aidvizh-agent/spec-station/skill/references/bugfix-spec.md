# Bugfix Spec

Режим для багов, где обычного фикса в чате мало: критический путь, прошлые попытки дали регрессии,
root cause неочевиден, нужна документация для комплаенса или команды.

Артефакт-замена требований — `bugfix.md`. Дальше всё как обычно: `design.md`, `tasks.md`, исполнение.

Тип спеки определяется сразу: **Feature** или **Bug**. На баге — `bugfix.md`, `requirements.md` не создаётся.

## Как описать баг

Четыре части, без них анализ будет гаданием:

1. **Reproduction steps** — точные условия, при которых баг воспроизводится.
2. **Current behavior** — что система делает сейчас (дефект).
3. **Expected behavior** — что должна делать.
4. **Constraints** — что **не** должно измениться.

Образец описания:

```
When a user submits a form with special characters in the name field
(e.g., O'Brien), the API returns a 500 error. It should accept the
input and save it correctly. The validation logic for email and
password fields should not be affected.
```

Четвёртое предложение — самое ценное: оно задаёт область сохранности и защищает от фикса, который ломает
соседнее.

## Фаза 1: анализ бага

Три секции в `bugfix.md`, синтаксис — EARS с двумя отличиями:

```md
# Bugfix: Special characters in the name field

## Current Behavior (Defect)

WHEN a user submits a form with special characters in the name field
THEN the system returns a 500 error

## Expected Behavior (Correct)

WHEN a user submits a form with special characters in the name field
THEN the system SHALL sanitize the input and save it successfully

## Unchanged Behavior (Regression Prevention)

WHEN a user submits a valid form
THEN the system SHALL CONTINUE TO process it exactly as before

WHEN a user submits an invalid email
THEN the system SHALL CONTINUE TO reject it with the email validation error
```

Что здесь важно:

- **В дефекте нет `SHALL`.** Дефект — констатация: `THEN the system <ошибочное поведение>`. `SHALL` появляется
  только там, где описано, как должно быть. Иначе требование и дефект неразличимы.
- **Ожидаемое — с `SHALL`**, как обычный критерий приёмки.
- **Сохранность — `SHALL CONTINUE TO`**, дословно. Формулировка «instead of being implicit about what should
  not change, the Bugfix Spec explicitly states it» — смысл всей секции: не оставлять неизменное молчаливым.
- Секция сохранности не должна быть пустой. Пустая означает, что рядом с багом нет работающего поведения —
  или что о нём не подумали.

## Фаза 2: дизайн

Исследуется кодовая база, находится root cause, пишется `design.md` с тремя блоками:

1. **Root cause analysis** — почему баг возникает, а не «где он проявляется».
2. **Proposed fix approach** — что именно правится и какой ценой.
3. **Properties to test for** — три группы:
   - текущая реализация даёт **неверное** поведение (баг существует);
   - исправленная реализация даёт **верное** поведение (фикс работает);
   - незатронутое поведение **продолжает работать** (регрессий нет).

## Property-aware evolution

Формализация для багфиксов. Обозначения:

- `C` — **bug condition**: предикат над входом, отделяющий «сломанные» входы от «рабочих». Условие именно
  над входом и состоянием, не над кодом.
- `P` — **postcondition**: что значит «исправлено».
- **Fix property**: `C ⇒ P`. На входах внутри `C` результат соответствует `P`.
- **Preservation property**: `¬C ⇒ поведение не изменилось`. Вне `C` всё осталось как было.

До написания кода `C`, `P` и гипотеза root cause показываются человеку на ревью. Это точка, где дешевле всего
обнаружить, что чинится не тот баг.

## Фаза 3: задачи

Ровно три задачи, в этом порядке:

1. **Bug-condition тесты** — входы внутри `C`, кодирующие `P`. Падают на нефиксированном коде. Это доказательство,
   что баг найден, а не описан.
2. **Preservation-тесты** — прогон **нефиксированного** кода на входах вне `C`, запись фактического поведения,
   ассерты. На нефиксированном коде проходят: нефиксированный код здесь и есть спецификация неизменного
   поведения. Без этого шага «регрессий нет» проверять нечем.
3. **Патч** — правка, после которой перепрогоняются обе группы: bug-condition краснеет → зеленеет,
   preservation остаётся зелёной.

Ветвление после патча:

- bug-condition **не** позеленел → гипотеза о root cause неверна, возврат к исследованию, а не «дожать патч»;
- preservation **сломалась** → у фикса есть побочные эффекты, патч сужается до необходимого;
- обе зелёные → баг закрыт с доказательством сохранности.

Для свойств используется property-based testing — на Python это Hypothesis; сочетание «красный-зелёный цикл
плюс differential testing» (сравнение поведения фиксированного и нефиксированного кода на одном входе).
См. `references/correctness.md`.

## Когда Bugfix Spec не нужен

Обычная правка в чате достаточна, если баг — опечатка, простая логическая ошибка или однострочное изменение
с понятной причиной.

Bugfix Spec берётся, когда:

- баг в критическом пути;
- прошлые попытки фикса вызывали регрессии;
- root cause сразу не виден;
- нужна документация для комплаенса или знаний команды.

## Границы

- **Bugfix Spec не превращается в Feature Spec.** Если root cause показал, что нужна новая функциональность,
  она уходит в отдельную Feature Spec, а bugfix остаётся про исходный дефект.
- Каждое требование сохранности должно быть проверяемым. «Работает как раньше» — не свойство; нужно
  конкретное наблюдаемое поведение.
- Если секция сохранности не заполняется, стоит усомниться в самой постановке: возможно, баг в зоне, где
  ничего и не работало, и это не багфикс, а фича.
