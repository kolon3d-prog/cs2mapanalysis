# Корректность: property-based тесты в спеке

Способ получить из требований проверки, которые не сводятся к выдуманным примерам.

## Что такое свойство

Свойство — универсальное утверждение о поведении системы:

> «Для любого набора входов, где выполняются такие-то предусловия, верно такое-то поведение.»

Оно ложится на EARS-требование напрямую:

| EARS | Свойство |
|---|---|
| `When a user submits a valid form, the Auth Service shall create an account.` | Для любой валидной формы аккаунт создаётся, и пароль хранится хешем. |
| `While an account is locked, the Auth Service shall reject login attempts.` | Для любого заблокированного аккаунта и любого пароля попытка отвергается. |

Из требования с `While` свойство получается подстановкой предиката; из `When` — генератором событий;
из `If` — генератором нежелательных входов.

## Формы свойств

Три, которые ищутся в первую очередь:

- **Инвариант** — утверждение всегда истинно для структуры данных. «В отсортированном списке каждый элемент
  не меньше предыдущего».
- **Round trip** — сериализация и разбор возвращают исходное значение. Для парсеров, сериализаторов,
  кодировщиков: «некоторая последовательность операций возвращает значение, с которого начали».
- **Идемпотентность** — повтор операции не меняет результат. Классика для `DELETE` в веб-API: удалить дважды —
  то же состояние, что удалить один раз.

## Где в спеке они живут

- **Дизайн** — из EARS-требований извлекаются свойства и генерируются тест-кейсы; у каждого свойства видна
  связь с исходным требованием и с задачей. Раздел `Testing Strategy` / `Unit Testing Strategy` в `design.md`.
- **Задачи** — тест-кейсы прогоняются против реализации. По умолчанию PBT **опциональны**: сначала можно
  сосредоточиться на основной реализации, свойства подключаются как отдельные задачи.
- **Падение** — показывается конкретный сценарий падения. Дальше человек выбирает: чинить реализацию, править
  тест или уточнять требование.

## Shrinking

При падении случайный вход автоматически минимизируется до **наименьшего**, который воспроизводит падение.
Часто это пустая строка или список из двух элементов.

Практическая ценность: «падает на случайном входе из 800 символов» и «падает на пустой строке» — разные
подсказки о причине. Первая уводит в чтение логов, вторая называет причину сразу.

## Инструменты

- **Hypothesis** (Python) — стратегии как генераторы, декоратор `@given`, интеграция с `pytest`; прогон по
  умолчанию — около 100 сгенерированных примеров.
- **Tyche** — визуализация покрытия сгенерированных входов, когда непонятно, что именно проверено.
- Терминология: property-based testing ≡ fuzzing ≡ generative testing.

## Специфика багфиксов

Свойства строятся для трёх групп (см. `references/bugfix-spec.md`):

| Обозначение | Смысл |
|---|---|
| `C` | условие бага: предикат над входом, отделяющий сломанные входы |
| `P` | постусловие: что значит «исправлено» |
| `C ⇒ P` | свойство фикса: на сломанных входах результат верен |
| `¬C ⇒ без изменений` | свойство сохранности: вне сломанных входов поведение прежнее |

Свойство сохранности проверяется **на нефиксированном коде**: сначала записывается фактическое поведение вне
`C`, оно становится эталоном, и только потом правится код. Без этого записывать «регрессий нет» нечем.

Сочетание получается двойным: красный-зелёный цикл плюс differential testing — фиксированная и нефиксированная
реализации сравниваются на одном и том же входе.

## Ограничения

- Это **свидетельство корректности, не доказательство**. Формальной верификации здесь нет.
- Слишком слабое свойство проходит, а поведение остаётся неверным. Свойство требует работы: «не падает» —
  тоже проходит, но ничего не проверяет.
- Не каждое требование маппится на чистое свойство: внешние сервисы и недетерминизм требуют моков или
  обычных example-based тестов.
- Нефункциональные требования (производительность, гонки) выражаются свойствами заметно труднее; для них
  остаются нагрузочные и конкурентные проверки.

## Что делать с найденным падением

1. Воспроизвести минимальный вход.
2. Решить, что именно неверно: реализация, свойство или требование.
3. Если неверна реализация — фиксить код, свойство оставить.
4. Если свойство было сформулировано неверно — править свойство и записать, почему.
5. Если требование неоднозначно — вернуться в `requirements.md`; свойство, которое нельзя сформулировать
   однозначно, обычно означает именно это.
