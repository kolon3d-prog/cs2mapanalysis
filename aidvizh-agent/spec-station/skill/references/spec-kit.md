# Улучшения из github/spec-kit

Kiro решает задачу «фича описана и разложена». `github/spec-kit` решает ту же задачу, но нашёл несколько
вещей, которых у Kiro нет. Они добавлены в этот режим — не как замена, а как надстройка.

## Что взять

### 1. Constitution — принципы проекта как проверяемый инвариант

Файл принципов проекта с версией и правилами изменения:

- принципы (обычно 3–5), каждый формулируется как обязательство;
- правила управления: как принимается поправка, кто её утверждает;
- версия: `MAJOR` — несовместимое изменение принципов, `MINOR` — новый принцип, `PATCH` — уточнение;
- даты: ратифицирована / последняя поправка.

Ценность: принципы проверяются как гейт на каждом анализе и сверке. Нарушение обязательства (`MUST`) —
находка уровня **critical**, а не «пожелание на будущее». У Kiro аналога нет: steering — это контекст,
а constitution — то, что можно нарушить.

Хранить рядом со спекой: `.kiro/constitution.md` или `.specify/memory/constitution.md`.

### 2. Clarify — до пяти точечных вопросов

Формализованный вопросник по требованиям:

- максимум пять вопросов, по одному за раз;
- у каждого — рекомендуемый вариант ответа плюс альтернативы;
- таксономия из девяти категорий (см. `references/quick-spec.md`);
- ответы записываются в раздел `## Clarifications` файла требований в виде `- Q: … → A: …`;
- после ответов — повторная проверка требований.

Отличие от уточняющих вопросов Quick Spec: здесь вопросы задаются **после** появления требований и по их
содержанию, не до генерации.

### 3. Checklist — проверка качества самих требований

«Unit-тесты для английского языка»: проверяется не код, а текст требований.

- категории: полнота, ясность, согласованность, измеримость, покрытие, границы, нефункциональные,
  зависимости, неоднозначности;
- ID пунктов (`CHK001…`) и ссылка на место в спеке (`[Spec §2.1]`);
- пометки `[Gap]`, `[Ambiguity]`, `[Conflict]`, `[Assumption]`;
- отметка `[x]` означает **ревьюер подтвердил**, а не «работа сделана»;
- пункты вида «проверить, что…» запрещены — это задача, а не вопрос о качестве текста.

Ценность: чеклист отделяет «требования написаны» от «требования хороши». Держится в
`checklists/<домен>.md` рядом со спекой.

### 4. Converge — append-only сверка кода со спекой

Проход после реализации: сравнить код со `requirements.md`, `design.md`, `tasks.md` и найти расхождения.

- типы находок: `missing` (требование не реализовано), `partial` (реализовано частично),
  `contradicts` (реализовано иначе), `unrequested` (в коде есть то, чего в спеке нет);
- результат **дописывается** в `tasks.md` секцией `## Convergence` с новыми задачами `T0xx`;
- если находок нет — файл не меняется **байт в байт**. Это не украшение: «ничего не найдено» должно быть
  отличимо от «файл перезаписан тем же содержимым».

Аналог в этом режиме — `/spec verify <feature>`.

### 5. Traceability-ID

Схема идентификаторов, которую удобно читать и грепать:

| ID | Что |
|---|---|
| `FR-###` | функциональное требование |
| `SC-###` | критерий успеха |
| `US#` / `AC#` | user story / критерий приёмки |
| `T0##` | задача из convergence |
| `CHK###` | пункт чеклиста |

В Kiro схема проще: `### Requirement N` плюс ссылки `_Requirements: 2.1_`. Для проекта с внешним трекером
полная схема удобнее — её можно связывать с тикетами. Выбирается одна схема на проект и держится.

## Чего в spec-kit нет

Не пытаться переносить:

- **EARS-грамматики нет.** Приёмка пишется как `Given/When/Then`, требования — как `FR-001 System MUST …`
  без триггеров `When/While/If/Where`. Здесь остаётся EARS: он даёт проверяемость и однозначность.
- **`bugfix.md` с секцией сохранности** — нет. У них багфикс идёт отдельным расширением с тремя документами
  (оценка → фикс → тест) и вердиктом `verified|partial|failed`. Идея вердикта полезна, механика — нет.
- **Property-based тестов в спеке** — нет.
- **Steering** — нет; его роль частично играет constitution плюс research.

## Разница в модели артефактов

Kiro: одна спека на фичу, `tasks.md` с чекбоксами и ссылками на требования.
spec-kit: `specs/<NNN-slug>/` с `spec.md`, `plan.md`, `research.md`, `data-model.md`, `quickstart.md`,
`contracts/`, `tasks.md`, `checklists/`; номер фичи последовательный (`NNN`, минимум три цифры) или
метка времени; ветка git от спеки независима.

Брать из этой модели стоит одно: **нумерованный префикс каталога** (`003-user-auth`), если спек в проекте
много и хочется видеть порядок создания. Kiro-раскладка без префикса остаётся значением по умолчанию —
иначе теряется совместимость.

## Как выбрать схему, если сомневаешься

- Проект небольшой, спеки читает человек — Kiro-схема: `Requirement N`, `_Requirements: 2.1_`.
- Требования связаны с внешним трекером, нужны трассируемые ID из кода и тестов — схема spec-kit:
  `FR-###`, `SC-###`, `CHK###`.
- Формат `tasks.md` **не менять**: он читается Kiro и нашим исполнителем одинаково.
