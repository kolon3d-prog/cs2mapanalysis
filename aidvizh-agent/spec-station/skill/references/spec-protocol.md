# Протокол спек-режима

Карта режимов, состояние, гейты, синхронизация. Частности — в справочниках по режимам.

## Каталог спеки

```
.kiro/specs/<feature>/
├── requirements.md   # или bugfix.md — оба сразу не бывает
├── design.md
├── tasks.md
├── spec.json         # состояние: режим, workflow, фаза, гейты (только этот порт)
└── research.md       # редко: сырые заметки исследования, когда дизайну нужен длинный фон
```

Имя фичи — **kebab-case**. Каталог можно переопределить переменной `SPEC_DIR`.

Почему именно `.kiro/specs`: это **формат Kiro**. Спека, созданная здесь, открывается в IDE Kiro, а спека,
созданная в Kiro, читается здесь. `spec.json` — наш, Kiro его игнорирует; ядро формата не тронуто.

`research.md` — исключение, а не правило. По умолчанию исследование живёт контекстом в тредах и переносится
прямо в `design.md`. Файл заводится только когда сырых заметок больше, чем дизайн может нести (замеры,
дампы, сравнение библиотек), и тогда `design.md` ссылается на него, оставаясь самодостаточным для ревью.

## spec.json

```json
{
  "feature": "user-authentication",
  "mode": "feature",
  "workflow": "requirements-first",
  "language": "ru",
  "phase": "design",
  "approvals": { "requirements": true, "design": false, "tasks": false },
  "created": "2026-09-21",
  "updated": "2026-09-21"
}
```

- `mode`: `feature` | `bugfix` | `quick`
- `workflow`: `requirements-first` | `design-first` (для `quick` и `bugfix` поле не значимо)
- `phase`: `requirements` | `design` | `tasks` | `implementation` | `done`
- `approvals`: пройден ли гейт фазы — по нему режим понимает, можно ли идти дальше
- `language`: язык переменных частей EARS (ключи `When/If/While/Where/shall` остаются английскими)

Файла нет — спека считается новой, спросить режим и workflow. Файл есть — **не спрашивать заново**,
продолжать с записанной фазы. Это и есть возобновление: `/spec <feature>` читает `spec.json` и `tasks.md`,
называет текущую фазу и невыполненные задачи.

## Гейты

| Переход | Вопрос | reason |
|---|---|---|
| требования → дизайн | Do the requirements look good? If so, we can move on to the design. | `spec-requirements-review` |
| дизайн → задачи | Does the design look good? If so, we can move on to the implementation plan. | `spec-design-review` |
| задачи → исполнение | Do the tasks look good? | `spec-tasks-review` |

- **Не** переходить дальше без явного одобрения: «yes», «approved», «looks good», «да».
- Спрашивать одобрение заново **после каждой** итерации правок, а не один раз за фазу.
- Цикл правок продолжается, пока не одобрено.
- Всплыли пробелы на этапе дизайна — вернуться к требованиям. Изменились требования — вернуться к задачам.
- Гейты бывают в порядке, обратном для Design-First: сначала «Does the design look good?», потом ревью
  производных требований.
- **Quick Spec** гейтов не имеет — но уточняющие вопросы заданы вперёд и зафиксированы.

## Поведение в каждой фазе

### Требования

- Создать `requirements.md`, если его нет.
- Первая версия — из сырой идеи, **без серии последовательных вопросов**.
- Код в этой фазе не исследовать.
- Учесть границы и отказы, UX, технические ограничения, критерии успеха.
- Точечные вопросы допустимы, но не превращаются в допрос.

### Дизайн

- Исследовать ровно столько, сколько нужно для решений; **отдельные research-файлы не плодить**.
- Ключевые находки — в тред, со ссылками на источники.
- Диаграммы обязательны там, где структура или поток неочевидны: Mermaid.
- Найден пробел в требованиях — вернуться.
- Обоснование решений писать текстом, структурную деталь нести диаграммам: не дублировать одно и то же.

### Задачи

- Дизайн превращается в серию шагов для исполнителя **в test-driven манере**: без больших скачков сложности,
  каждый шаг опирается на предыдущий, заканчивается соединением частей.
- Ничего не тащить из дизайна повторно: задача описывает работу, а не повторяет контракт.
- Висящего кода не остаётся: всё, что создано, подключено на предыдущем или текущем шаге.
- Режим только создаёт артефакты. Исполнение — отдельный проход (`/spec-tasks run`), и после одобрения задач
  режим **останавливается**, а не начинает кодить сам.

## Профили запуска

| Что | Как |
|---|---|
| Новая спека | `/spec-new <краткая идея>` — спросит режим и workflow один раз |
| Продолжить | `/spec <feature>` — читает `spec.json`, называет фазу и невыполненные задачи |
| Форсировать фазу | `/spec <feature> design` — начать указанную фазу |
| Все задачи волнами | `/spec-tasks run <feature>` |
| Одна задача | `/spec-tasks run <feature> 2.3` |
| Только обязательные | `/spec-tasks run <feature> --required` (опциональные `- [ ]*` пропускаются) |
| Аккуратный режим | `/spec-tasks run <feature> --sequential` — маркеры `(P)` игнорируются |
| Анализ требований | `/spec-analyze <feature>` |
| Сверка кода со спекой | `/spec verify <feature>` (append-only, см. `spec-kit.md`) |
| Состояние всех спек | `/spec status` |
| Явно подтянуть спеку в контекст | `#spec:<feature>` — подставить все три файла |

## Ссылка на спеку в разговоре

`#spec:<feature>` подставляет в контекст **все** файлы спеки — так работа с реализацией не разъезжается
с задокументированным поведением. Примеры:

```
#spec:user-authentication implement task 2.3
#spec:user-authentication update the design file to include password reset flow
#spec:user-authentication does my current implementation meet the acceptance criteria for task 7.1?
#spec:user-authentication why did we choose JWT over session-based authentication?
```

В файлах спеки работают ссылки на живые файлы: `#[[file:relative/path]]` — например, OpenAPI-схема в
`design.md` как источник контракта.

## Итерации и синхронизация

- Изменились требования → «Refine» дизайна, затем «Sync Files» задач: новые требования получают свои задачи.
- Изменился дизайн (Design-First) → перепроверить производные требования на осуществимость, затем Sync Files.
- **Sync Files**: сверить чекбоксы задач с фактически реализованным кодом и отметить выполненное. Тот же
  результат даёт «Check which tasks are already complete» — режим просматривает код и отмечает задачи сам.
- Одна спека на фичу. Не одна спека на репозиторий: крупный проект держит много спек в `spec.json`-совместимой
  раскладке `.kiro/specs/`, и они не конфликтуют между собой.

## Импорт существующего

- Готовое описание требований (`foo-prfaq.md`, PRD, выгрузка из JIRA) → положить в репозиторий и сказать
  `#foo-prfaq.md сгенерируй спеку из этого`. Режим читает файл и строит требования и дизайн.
- Готовая архитектура → Design-First: скормить диаграмму или текст, формализовать в `design.md`, вывести
  требования.
- Схемы можно картинкой (PNG/JPG) — включая фото доски.

## Гигиена

- Все файлы спеки версионируются вместе с кодом: они часть проекта, а не рабочий мусор.
- Общая спека для нескольких репозиториев — центральный репозиторий спек + git submodule или симлинк.
- Пути внутри спек — относительные.
