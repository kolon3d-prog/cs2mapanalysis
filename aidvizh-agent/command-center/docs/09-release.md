# Версия набора и обновление

Версия набора — один файл `VERSION` в корне диска. Он **единственный источник**: его читают
`center status` (строка «версия набора») и `center version` (состав и ритуал). Автоинкремента нет:
версию меняют руками и осознанно, потому что она обещает состояние всего диска, а не факт запуска.
Текущее значение — в файле `VERSION` (единственный источник); числа в доках не хардкодим: расхождение с фактом ловит `bin/docs-check.sh`.

## Из чего складывается

`center version` печатает:

- саму версию и путь к `VERSION`;
- **состав** — по каждому проекту, какой git-коммит лежит на диске и есть ли несохранённые правки
  (проект без `.git` так и помечен: «не git-репозиторий»);
- **правило бампа** (ниже);
- **ритуал релиза** (ниже), чтобы его не искали в доках.

`center version --json` — то же машине: `{version, source, root, policy, projects[], ritual[]}`. В `root`
и в каждом проекте есть commit SHA, ветка и число tracked/untracked-правок.

`center release --to <путь>` — отдельная операция выпуска: она отказывается собирать грязный корень
или вложенный репозиторий без `--allow-dirty`, не кладёт в релиз `.git`, runtime-базы, багрепорты
и файлы с именами `.env*`, `*.key`, `*.pem`, `secrets*`, а рядом кладёт `manifest.json` и `.sha256`.

## Правило бампа

| что меняем | что бампаем | пример |
|---|---|---|
| правки внутри станции: те же команды, те же контракты | **patch** | 5.0.3 → 5.0.4 |
| новый проект, новая команда центра или новое поле реестра | **minor** | 5.0.3 → 5.1.0 |
| смена контракта между станциями (несовместимая: стороны обновляются вместе) | **major** | 5.0.3 → 6.0.0 |

Реестр — часть контракта: `update`/`outdated` в записи проекта, форма `outdated --json` у станции,
профили MCP-серверов. Новое поле в реестре, которое старая станция не понимает, — это **minor**;
переименованное поле, на которое станция опирается, — **major**.

## Ритуал релиза

1. **Правки** — в станциях и центре; тесты каждой затронутой станции зелёные (`bats tests/*.bats`).
2. `center update` — догнать установленное до диска: центр зовёт у проектов их же команды обновления,
   ничего не дублирует. Сначала полезно посмотреть `center update --dry-run all` (план: кому уходит
   флаг «ничего не менять», кого центр всерьёз не зовёт) и `center outdated` — что устарело.
   Флаги, которых у центра нет (`--prune` у mcp-station), адресуют станции напрямую:
   `center run mcp-station update --prune --yes`.
3. `center check` — связи (`doctor`) и сквозной прогон наборов.
4. **Правка `VERSION`** — по правилу выше, руками. Это и есть момент выпуска: до него версия
   описывает то, что уже лежит на диске, после — новый набор.
5. `center version --json` — сверить корень, вложенные репозитории, коммиты и грязь.
6. `center release --to <путь>` — собрать безопасный архив с manifest и SHA-256; для диагностической
   сборки грязного состояния нужен явный `--allow-dirty`.

Чего ритуал **не** делает: не трогает `VERSION` сам, не поднимает версию за каждый запуск или
изменение файла, не гоняет сеть и не спавнит MCP-серверы (`center verify` — отдельная живая проверка
соединений, а не шаг релиза: она долгая и не бесплатная). Обновление и выпуск — две разные операции: `center update`
приводит установленное к диску, версия объявляет, что именно на диске лежит.

## Кто умеет обновляться

Команда обновления живёт в реестре (поле `update`) — это команда **самого проекта**, а не центра:

- `mcp-station` — `bin/mcp-station.sh update` (reconcile: переписать изменившиеся записи, добавить
  новые по профилю, `--prune` снимает сирот) + машинная сверка `bin/mcp-station.sh outdated --json`;
- `cli-station`, `skills-station`, `spec-station`, `pi-plugins-station`, `modes-station`, `memory-station`, `wiki-station` —
  их собственный `install` (идемпотентен: повторный прогон и есть обновление); у плагинов pi сверка версий
  с npm объявлена отдельно (`outdated --json`);
- `sysprompt`, `omp-zen-free`, `camoufox-research`, `fedora-windows-look` — их установщики
  (`install.sh`, `scripts/install.sh`) из того же клона;
- `skills-hub`, `prompt-station`, `personas`, `agent-bundle`, `totp`, `test-center`, `cleanup-station`,
  `dump (в рантайме)` — команды нет, и в реестре стоит `updateNote` с причиной: у хаба скиллы
  обновляются поштучно, у prompt-station прошивка ставится по имени, данные и доки обновляются
  вместе с диском, test-center ничего не держит, cleanup-station умеет сносить (для «снести и
  поставить заново» есть `center fresh`).

Проверить, что изменилось, можно `center outdated`: статус `updates` — сверка объявлена и говорит,
что устарело; `unknown` — сверки нет, и в `detail` одна строка почему. Врать в эту строку центр не
имеет права: лучше честное «проверить нечем», чем выдуманное «всё свежее».

## Как центр понимает флаг «ничего не менять»

В режиме `--dry-run` центр передаёт проекту флаг только тогда, когда тот **сам его объявил**: центр
читает текст команды (и движок, на который разворачивается тонкая обёртка `.sh`) и ищет там
`--dry-run` (на Windows — `-WhatIf`). Запускать команду с `--help` для проверки нельзя: у части
установщиков (`fedora-windows-look/install.sh`) он всё равно создаёт ссылки. Не нашёл флаг — центр
ничего не запускает и показывает строку плана, а не зовёт всерьёз.

После настоящего обновления центр перепроверяет связи **тем же** `doctor`, а не второй проверкой
рядом: установка могла увести симлинки или потерять MCP-регистрации, и это видно сразу.
