# MCP

`mcp-station` держит каталог серверов (`catalog/*.json`, без секретов и без путей) и раскладывает их в
клиентов: omp/pi — `mcpServers` со `command`/`args` (http — `url`+`headers`), opencode — `mcp` со
`type: local`/`remote`. Один каталог на три клиента: `mcp-station install` ставит всё, `status` показывает
расхождение, `check` — чего не хватает (файлы серверов, файл ключей, переменные).

Ключи живут в одном файле `~/.config/opencode/secrets/env` (права 600), в конфиги клиентов не попадают:
у omp/pi значение подставляется на старте сервера (`bash -lc` + `printf`), у opencode — при установке.
Установка без ключей не падает: сервер регистрируется, а заголовок opencode получает заглушкой
`{env:VAR}` (формат сохраняется, `Bearer` остаётся). После `keys.sh import` повторный
`mcp-station install` подставляет значения из файла. Управление: `mcp-station/bin/keys.sh list|add|import|remove`
(сколько угодно ключей на провайдера: `VAR`, `VAR_2`, …).

Пул ключей с переключением: `mcp-station install exa lazyweb --pool` — сервер идёт через шим
`~/.local/bin/mcp-keypool`, который при 401/403/429/5xx молча берёт следующий ключ и запоминает рабочий
(`MCP_STATION_POOL_STRATEGY=round-robin` — по кругу). Для stdio-серверов (`npx`) перебора нет: они читают
ключ на старте.

Подтверждения на опасные тулы: каталог объявляет поле `approval`, и станция пишет гейты в родные
механизмы клиентов — opencode `permission["<сервер>_<тул>"] = "ask"`, omp
`tools.approval["mcp__<сервер>_<тул>"] = "prompt"` (у pi такого механизма нет). Сейчас так закрыт
`skills_install` у `skills-hub`: установка чужого скилла идёт с полными правами агента.

У pi MCP нет из коробки: работает через расширение `pi-mcp-adapter` (`pi install npm:pi-mcp-adapter`).

## Windows: нативный запуск без bash

Unix-форма записи часто идёт через шелл (`bash -lc` с раскрытием `$HOME` или загрузкой ключей из файла).
В конфиге Windows шелла нет, а `bash` в PATH нередко оказывается заглушкой из дистрибутива WSL: на `-lc`
она печатает «поставь дистрибутив» и выходит с нулём — клиент получает мёртвый сервер, а `check` молчит
зелёным (так и вышло: семь записей из восьми были нерабочими).

Поэтому у каждой stdio-записи каталога есть `argvWindows` — тот же состав команды без bash; исключения —
три отладочные Unix-записи без Windows-рантайма (`bpftrace`, `lldb`, `radare2`), их станция без
настоящего Git Bash не ставит строкой (разбор — `mcp-station/README.md`, «Платформы отладочных записей»).
Что в нём встречается:

- `$HOME` и `$STATION` станция раскрывает сама на момент установки (в конфиге Windows раскрывать их
  некому), разделители приводятся к виндовым;
- серверы с ключами (`firecrawl`, `jev`, `serper`, `tavily`) идут через `bin/entryenv.mjs`: он читает
  файл ключей целиком и запускает то, что стоит после `--`, — это буквальный эквивалент
  `set -a; . file; set +a`. Ключи остаются только в файле секретов, в конфиг не попадают;
- `npx`-серверы (`chrome-devtools`, `inspo`, `playwright`) зовутся как `cmd.exe /c npx …`: `npx` на
  Windows — это `.cmd`-шим, а node не запускает `.cmd` напрямую; `cmd.exe` есть всегда;
- `camoufox` получает профиль тулов из `envWindows` — станция пишет его клиенту в `env` (omp/pi) или
  `environment` (opencode), а суженный владельцем профиль не перетирает;
- заголовки http-серверов на Windows omp и pi получают литералом из файла ключей (как opencode):
  `!`-подстановка — это bash. Нужен `{env:VAR}` — `MCP_STATION_OMP_HEADERS=env` / `MCP_STATION_PI_HEADERS=env`.

Запись без `argvWindows` на Windows **не ставится**: станция говорит строкой контракта и возвращает 1.
Если настоящий Git Bash (Git for Windows) в системе есть, такая запись ставится с абсолютным путём к
`bash.exe`. Заглушка WSL не считается башем никогда — ни в `check`, ни в `verify`, ни при установке, —
и `verify` вместо мусора заглушки говорит `spawn-failed` с причиной. Всё, что станция делает с конфигами,
она делает без шелла: пул ключей на Windows идёт через `cmd.exe /c mcp-keypool.cmd <сервер>`, а пустой
файл ключей создаётся при установке (600) вместе с подсказкой `bin/keys.ps1 add <сервер>`. Старые `.bak`
конфигов держатся по пять рядом с конфигом, остальные уносятся в рантайм
(`~/.local/state/mcp-station/dump/`), а не удаляются. Ветка Windows прогоняется на Linux:
`MCP_STATION_PLATFORM=win32` (PATH и через `;`, и через `:` как из Git Bash).

Отдельно: запись, попавшая не в свою форму (omp-вид `command`+`args` внутри opencode, без `type`),
станция читает как свою и починяет `update` — раньше она считалась чужой и оставалась кривой. Своя же
запись в Unix-форме (`bash -lc …`) на Windows узнаётся как своя и переписывается нативным `argvWindows`
тем же `update`; чужая (например camoufox с абсолютным путём venv от установщика проекта) не трогается
без имени.

## Память и вики через MCP

Два сервера каталога дают агенту долговременную память и доступ к вики — оба локальные, без ключей:

- `basic-memory` (`memory-station`) — заметки `~/basic-memory/{code,life,projects}` + SQLite-индекс:
  `write_note`, `search_notes`, `read_note`, `build_context`;
- тот же `basic-memory` обслуживает вики: каждая вика из `wiki-station/wikis.json` заводится отдельным
  проектом (`wiki-vibecoding`), поэтому `search_notes(query, project="wiki-...")` ищет по постам вики.

Ставится и то, и другое станциями: `memory-station install`, `wiki-station install` (обе идемпотентны,
обе зовут `mcp-station install <сервер>` — каталог MCP остаётся один).

## Кто ждёт сервер в клиентах

Проект вне каталога станции тоже бывает с MCP: `camoufox-research` ставит свой сервер сам (в
`opencode.json`, функции `scripts/install_mcp.py`), а его окружение живёт в рантайме
(`$HOME/.venvs/camoufox-research`, браузер — `$HOME/.cache/camoufox`), не в клоне. Штатная регистрация
во всех трёх клиентах идёт через каталог `mcp-station` (`catalog/camoufox.json`). Чтобы центр это
видел, в реестре есть поле `expectMcp` — список имён серверов, которые проект ждёт у клиентов
(`camoufox-research` объявляет `camoufox` — так его регистрирует и установщик проекта, и станция).

`center doctor` читает конфиги всех трёх клиентов и печатает отдельной строкой, у кого из них сервер
заведён, а у кого нет:

    —    camoufox (camoufox-research): есть у omp, opencode; нет у pi

Строка помечена `—`, а не `ok`/`FAIL`: она справка, а не приговор. Код возврата `doctor` держат связи
(`expectLinks`) и каталоги, а сама регистрация — шаг `mcp-station install` (у станции свой `check`).
Заведён ли сервер в каждом клиенте, видно и в `center status` — в строке проекта как `mcp 2/3`.

## Живая проверка: `center verify`

Запись в конфиге ещё не значит рабочее соединение. Отвечает ли сервер по протоколу — проверяет
`center verify`: он берёт ту самую запись, что лежит в конфиге клиента (у omp/pi ключи подставляются на
старте через `!`-команду, у opencode — литералом при установке), поднимает сервер и ждёт `initialize`.

    center verify                                   # все три среды, таймаут 20 с
    center verify --client omp wiki basic-memory     # одна среда, два сервера
    center verify --exclude playwright,chrome-devtools,stealth-browser,camoufox

Разделение простое: `doctor` — «есть ли запись» (статика, дёшево, читает файлы), `verify` — «работает ли
соединение» (живой хендшейк, спавнит настоящие серверы, часть поднимает браузер). Состояния сервера:
`connected`, `no-handshake`, `spawn-failed`, `timeout`, `http-error` — что каждый значит, в
[07-verify](07-verify.md). Код возврата 1, если сервер не ответил или харнесса (omp/opencode/pi) нет;
подробности и разбор провалов — [08-troubleshooting](08-troubleshooting.md).

## Браузер: блокировка и «запись новее запуска»

Два браузерных сервера на одной машине дерутся за профиль, поэтому тяжёлые браузерные прогоны
(`camoufox`, `playwright`, `chrome-devtools`, `stealth-browser`) ходят через один замок —
`~/.local/state/command-center/browser.lock` (переопределяется `CENTER_BROWSER_LOCK`): в нём pid, команда
и время. Протухшую блокировку (pid мёртв или старше TTL, по умолчанию 30 минут — `CENTER_BROWSER_LOCK_TTL`)
снимает следующий пришедший и говорит об этом. Кто держит сейчас — `center ps`, взять и снять — сама
`mcp-station verify`; центр замок только читает и никого не поднимает.

Второе — `session_stale`: клиент читает конфиг на старте, поэтому свежая запись в уже идущей сессии не
видна («тулы есть в конфиге, а агент их не видит»). `center verify --json` и `center ps --json` помечают
такую среду полем `session_stale` и зовут перезапуск клиента; нет процесса клиента — поля нет вовсе,
«не знаю» честнее выдумки.
