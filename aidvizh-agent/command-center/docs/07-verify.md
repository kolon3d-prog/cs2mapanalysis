# Проверки

| что | чем | что означает |
|---|---|---|
| связи и регистрации | `center doctor` | симлинки ведут туда, куда заявлено; MCP-конфиги читаются и содержат серверы, а ожидания проекта (`expectMcp`) показываются построчно у всех трёх клиентов |
| **работает ли MCP** | `center verify` | живой хендшейк: харнессы (omp/opencode/pi) стоят и каждый сервер из конфига клиента отвечает по протоколу — спавнит настоящие серверы, не бесплатно; провал чужой записи (свой сервер покупателя) дом не валит — она строкой «чужое, не считаем» |
| состояние диска | `center status` | проекты на месте, точки входа есть, git-состояние, живые ссылки |
| предпосылки | `center prereqs` | node/npm/bun/git/gh/jq/bats/curl с подсказками, чем доставить |
| что устарело | `center outdated` | зовёт объявленные сверки проектов (`outdated --json` у mcp-station и pi-plugins-station) и сводит: `updates`/`current`, а где сверки нет — `unknown` и одна строка почему |
| обновление | `center update [имена\|all]` | зовёт команды обновления из реестра (`--dry-run` — план), после настоящего прогона связи перепроверяет тем же `doctor` |
| версия набора | `center version` | из чего складывается версия (`VERSION` + снимок коммитов) и по какому правилу её бампают (см. [09-release](09-release.md)) |
| сквозной прогон | `center check` | doctor хаба + наборы тестов, которые зовёт `skills-hub/contrib/skills-hub-check.sh` (сейчас 19 файлов bats, 407 тестов — не все наборы диска) + живая проверка MCP из часовой проверки |
| числа в доках | `bin/docs-check.sh` (Windows: `bin/docs-check.ps1`) | сверяет числа и списки в README/docs с фактом (реестр, коллекция, наборы тестов, `VERSION`) и падает строкой «сказано N, на деле M»; полный `center check` требует gate, `--best-effort` оставляет мягкий пропуск |
| платформенная полнота | тот же гейт | у каждого `.sh` на диске обязан быть сосед `.ps1`, иначе путь лежит строкой в `platform-exceptions.txt` с причиной; протухшее исключение — тоже расхождение |
| строгий режим скриптов | тот же гейт | у каждого `.sh` в первых 25 строках обязан стоять `set` с `-u` и `pipefail` (где `-e` мешает — `set -uo pipefail`); нарушитель — либо правка, либо строка «путь\|причина» в `strict-exceptions.txt`; протухшая строка — тоже расхождение |
| покрытие прогона | тот же гейт | список наборов bats, которые зовёт `skills-hub/contrib/skills-hub-check.sh`, сверяется со всеми наборами диска: непокрытый набор обязан быть строкой «путь\|причина» в `check-coverage-exceptions.txt`; протухшая строка — тоже расхождение |
| диск и ссылки вне диска | `bin/sentinel.sh` (Windows: `bin/sentinel.ps1`) | то, что центр проверить не может: сам он лежит на диске. Сторож отвечает «диск DATA на месте и живы ли ссылки в `$HOME`» — код 0 и одна строка, либо код 1 и список мёртвого (`--json` — машине, `--quiet` — режим таймера) |
| бэкап набора | `center backup --to <путь>` | архив набора (`tar.zst`, иначе `tar.gz`) + `.sha256` рядом, проверка чтением оглавления, ротация по `--keep`; цель на том же устройстве, что набор, отвергается — «тот же диск — это не бэкап» (снимается `--force-same-disk`) |
| релиз набора | `center release --to <путь> [--allow-dirty]` | безопасные исключения, manifest с commit/branch вложенных репозиториев и `.sha256`; грязный корень или вложенный репозиторий без явного флага отвергаются |
| проверка бэкапа делом | `center restore --from <архив\|каталог> --to <пустой каталог>` | распаковка **в сторону** и сверки копии: `VERSION`, реестр и каталоги проектов, гейт доков распакованного набора; `.sha256` обязателен по умолчанию, структура архива проверяется до распаковки, непустой каталог и путь внутрь набора отвергаются — живой набор команда не трогает |
| то же по расписанию | systemd-таймер `skills-hub-check` | раз в час: doctor + те же наборы + живая проверка MCP одной строкой (`MCP: omp 8/8 · opencode 8/8 · pi 8/8`, при провалах — `MCP: FAIL`); `journalctl --user -u skills-hub-check`. Ставит `skills-hub/contrib/install-units.sh`, включает `systemctl --user enable --now skills-hub-check.timer`. Важно: `cleanup-station clean-units` этот юнит снимает по замыслу («снос нашего») — после сноса его ставят и включают заново той же парой команд |
| сторож и бэкап по расписанию | таймеры центра `center-sentinel` (каждые 15 минут) и `center-backup` (ночью) | юниты и ЛОКАЛЬНАЯ обёртка `$HOME/.local/state/center/center-local.sh` (копия, не ссылка на диск) ставятся `contrib/install-units.sh` — в плане установки это шаг «сторож и бэкап набора» (`center bootstrap`, `center fresh`); снимает их `cleanup-station clean-units` вместе с локальной обёрткой, а цель бэкапа и архивы не трогает. Цели бэкапа — по строке на цель, у каждой свой `--keep`; неудача одной цели не отменяет остальные, но код выхода 1. Живы ли сторожа, видно строкой в `center status`. Диск не примонтирован — обёртка говорит «диск DATA не примонтирован, ссылки в $HOME мертвы» и выходит с 1, поэтому юнит падает видимо, а не молчит; `journalctl --user -u center-sentinel` |

Отдельные станции умеют своё: `skills-manager doctor` (зависимости, симлинки, MCP-пути, gh auth),
`mcp-station check`, `cli-station status/doctor`, `skills-station verify/status`, `spec-station verify/status`,
`pi-plugins-station verify/status/outdated`, `prompt-station verify`, `cleanup-station plan`.

`pwsh` 7.6.6 стоит на машине, поэтому Windows-обёртки станций и их тесты гоняются по-настоящему
(`skip=0` в наборах); «не проверено» в README станций остаётся только про настоящую Windows. Ветки
движков, которые включаются только на Windows, проверяются на Linux подменой платформы
(`CENTER_PLATFORM=win32`, `MCP_STATION_PLATFORM=win32`, `CLI_STATION_PLATFORM=win32`): подложенный PATH
с `;`, свои `PATHEXT`, `.ps1`-соседи вместо `.sh` и заглушка WSL в PATH, которая не должна считаться bash.

## Сторож набора и бэкап: `sentinel` / `backup`

Центр — часть набора, а набор лежит на диске DATA: пока диск на месте, центр видит всё, а если диск
отвалился, то центр недоступен ровно тогда, когда о нём хотелось бы спросить, и симлинки в `$HOME`
при этом молча мертвы. Поэтому у сторожа два требования: он запускается **не с диска** и говорит
строкой, когда диска нет.

    bin/sentinel.sh                # 0 — всё живо (одна строка); 1 — список мёртвого
    bin/sentinel.sh --json         # машине: диск, точка монтирования, ссылки, версия, проблемы
    bin/sentinel.sh --quiet        # режим таймера: молчит, пока всё живо

Проверки сторожа (движок `bin/sentinel.mjs`, обёртки `bin/sentinel.sh` и `bin/sentinel.ps1`):

- каталог набора существует и лежит на своём диске: точка монтирования ищется в `/proc/mounts`,
  и корневая ФС ею не считается — после отвала диска каталог достаётся корневой ФС, и это надо назвать;
- каждая ссылка из `expectLinks` всех проектов реестра резолвится в существующую цель **внутри набора**
  (цель вне набора — тоже поломка: после пропажи диска она не оживёт);
- `VERSION` читается.

На Windows точек монтирования нет — там честный ответ только про существование пути, и это видно в
`--json` (`mounted`), а не выдаётся за проверку диска.

Юниты ставит `contrib/install-units.sh`:

    bash contrib/install-units.sh
    systemctl --user enable --now center-sentinel.timer    # каждые 15 минут
    systemctl --user enable --now center-backup.timer      # ночью (если есть цель бэкапа)

Юниты (`center-sentinel.service/.timer`, `center-backup.service/.timer`) зовут не скрипт с диска, а
ЛОКАЛЬНУЮ обёртку — `$HOME/.local/state/center/center-local.sh`, поставленную **копией** (не ссылкой).
Обёртка проверяет, что диск примонтирован, и если нет — печатает «диск DATA не примонтирован, ссылки
в $HOME мертвы» и выходит с 1: юнит падает видимо. Сторож, живущий на том же диске, что и сторожимое,
сторожем не является. Цели бэкапа обёртка берёт из `$HOME/.config/center/backup.target` — по строке
на цель, второй столбец это свой `--keep` (локальная копия и оффлайн-носитель): идёт по порядку и не
отменяет остальные из-за одной неудачи, но о неудаче говорит строкой и кодом 1. Нет файла —
бэкап-юниты не ставятся, и установщик говорит об этом строкой. Живы ли сторожа, видно из `center status`
(в конце — строка на юнит: включён ли таймер, чем кончился последний прогон, куда смотреть при провале).

Бэкап набора — команда центра:

    bin/center.sh backup --to /media/backup/aggg --keep 3   # архив + .sha256, держим три последних
    bin/center.sh backup --dry-run --to …                   # план: путь, сжатие, что уберёт ротация
    bin/center.sh backup --json --to …                      # машине: путь, размер, sha256, версия

`tar.zst` (если есть zstd, иначе `tar.gz`) без кэшей (`node_modules`, `__pycache__`, `.pytest_cache`,
`*.pyc`, `*.log`), `.git` — и корневой, и подпроектов — внутрь; рядом `.sha256`, проверка чтением
оглавления (пустой архив или архив с кэшем удаляется, а не выдаётся за бэкап), ротация старых по
`--keep`. **Тот же диск — это не бэкап:** если цель на том же устройстве, что и набор (`st_dev`),
команда отказывается работать и возвращает 1; `--force-same-disk` снимает отказ, если бэкап нужен
именно там.

## Платформы: кто на какой ОС работает

Один движок — обёртка на каждую ОС. У гейта доков это `bin/docs-check.mjs` + `bin/docs-check.sh` и
`bin/docs-check.ps1`; у установки плагинов — `contrib/install-plugins.mjs` + два таких же соседа.
Обёртка только выбирает запускалку (`node`), поэтому вердикт и строки на bash и на PowerShell одни
и те же: их печатает движок.

У проекта в реестре есть поле `platforms` (по умолчанию все три — linux/darwin/win32; у честно
Unix-only станции подмножество: `fedora-windows-look` — только linux). Проект, которого на этой ОС
нет, центру не мешает: `center status` печатает вместо прочерков строку «не поддерживается на этой
ОС (platforms: …)», `center run`/`update` говорят то же и выходят нулём — искать точку входа, которой
на этой ОС и не должно быть, центр не станет.

    center status                    # у fedora-windows-look на Linux — «только linux»
    CENTER_PLATFORM=win32 center status   # та же станция: «не поддерживается на этой ОС (platforms: linux)»

`CENTER_PLATFORM` — тот же хук, которым центр определяет ОС (по умолчанию — сама платформа); им
удобно посмотреть, что скажет центр на чужой машине, не заводя её.

Платформенная полнота — часть гейта доков, и проверяется в обе стороны:

- каждый `.sh` на диске обязан иметь соседа `.ps1`; если порта нет, путь обязан лежать в
  `../platform-exceptions.txt` строкой «путь|причина» — и причина пишется словами, а не «так вышло»;
- каждая строка исключения обязана быть живой: файл обязан существовать и `.ps1` у него быть не
  должно. Появился порт — строку убирают, иначе гейт падает на протухшем исключении.

Туда попадает только системное: systemd-юниты и таймеры, cron, git-хуки, docker-вход, Linux-only
станция и чужие скрипты из коллекции скиллов. Всё остальное — порт: обычно тонкая обёртка над общим
`.mjs`-движком, поэтому логика остаётся в одном месте, а не разъезжается между ОС.

Наборы тестов оффлайновые: подменяют сеть и пакетные менеджеры заглушками, домашний каталог — временным,
так что их можно гонять на живой машине без последствий.

## Живая проверка MCP: `center verify`

`doctor` статический: он читает конфиги клиентов и отвечает на вопрос **«есть ли запись»**. `verify`
живой: поднимает серверы по протоколу MCP и отвечает **«работает ли соединение»** — причём именно та
запись, что лежит в конфиге клиента (у omp/pi ключи подставляются на старте, у opencode — при установке),
а не «рендер из каталога станции». Смысл в этом: клиент должен получить рабочее соединение.

    center verify                                                # три среды, таймаут 20 с
    center verify --client opencode --timeout 40                 # одна среда, больше времени
    center verify wiki basic-memory                              # только эти серверы
    center verify --exclude playwright,chrome-devtools,stealth-browser,camoufox
    center verify --json                                         # машине (см. ниже)

Центр ничего не проверяет сам: харнессы отдаёт `cli-station status --json` (поле реестра
`harnessStatus`), живые соединения — `mcp-station verify --json` (поле `mcpVerify`). Проверка **не
бесплатна**: она спавнит настоящие серверы, и часть тяжёлая — `playwright`, `chrome-devtools`,
`stealth-browser`, `camoufox` поднимают браузер. Поэтому есть `--timeout`, `--exclude` и выбор серверов
по имени, а в цепочках (`center fresh`, `center bootstrap`) шаг стоит отдельно и о его длине сказано
в плане заранее.

**Чужие записи не считаем провалами.** В конфигах клиентов лежат не только наши серверы: у покупателя
уже стоит свой MCP-сервер, чужой установщик положил свою запись. Станция их не ставила и за них не
отвечает, поэтому провал такой записи — не провал дома: код 1 `center verify` даёт только по своим.
Своя ли запись — не догадка, а та же сверка трёх сторон, что у `outdated` (каталог, состояние станции,
конфиг клиента): состояние помнит отпечаток поставленного, а форму записи сверяет каталог. Чужие провалы
видны строкой `чужое, не считаем: <клиент>/<имя> — <состояние>` и полем `foreign_failed` в `--json`;
наши — как раньше, списком `провалы:` и числом в строке `итог`. Если состояние станции не прочитать,
формой не гадаем: своим считаем то, чьё имя есть в каталоге, и об этом сказано полем `owners: "catalog"`.

Что значит строка отчёта:

    omp       ~/.omp/agent/mcp.json      connected 8/8
    opencode  ~/.config/opencode/opencode.json   connected 6/7
    провалы:
      opencode/wiki — timeout (20000 мс): нет ответа на initialize
    итог: серверов 22, connected 21, провалов 1, харнессов не хватает 0
    чужое, не считаем: opencode/playwright — spawn-failed

Состояния сервера (их отдаёт `mcp-station verify`):

| состояние | что случилось | куда смотреть |
|---|---|---|
| `connected` | сервер ответил на `initialize` | всё в порядке |
| `no-handshake` | процесс жив, но по протоколу не ответил | сервер печатает что-то своё в stdout — [08-troubleshooting](08-troubleshooting.md) |
| `spawn-failed` | не запустился (нет команды, ключа, записи в конфиге) | `mcp-station check`, `keys.sh list` |
| `timeout` | не ответил за `--timeout` секунд (тяжёлые поднимаются дольше) | дать `--timeout` больше или исключить `--exclude` |
| `http-error` | http-сервер ответил ошибкой (401/403 и т.п.) | ключ/заголовок сервера |

Код возврата `center verify` — 1, если пропал харнесс (omp/opencode/pi не стоит) или не ответила хотя
бы одна **наша** запись сервера. Чужие записи провалом дома не считаются — они строкой «чужое, не
считаем» и полем `foreign_failed`, код при них нулевой. Машинный отчёт:

    {"ok":true,"harness":[{"name":"omp","installed":true,"version":"omp/18.1.21"}],
     "mcp":{"omp":{"connected":8,"failed":0,"foreign_failed":0}},
     "summary":{"harness_missing":0,"servers_failed":0,"foreign_failed":0}}

У каждой строки сервера в `--json` станции и центра есть `ours` — своя запись или чужая; у сводки —
`failed_ours` (свои) и `foreign_failed` (чужие), `failed` остаётся их суммой; чужие провалы перечислены
отдельным массивом `foreign_failures`. Если состояние станции не прочитать, в отчёте стоит
`owners: "catalog"` — принадлежность определена по каталогу.

Если саму проверку провести нечем (станция не ответила, её команды нет в реестре) — `ok:false`, поле
`error` с причиной и код 1: молчаливых нулей вместо ответа центр не печатает.

## Сквозная проверка на любой ОС: test-center

`test-center/bin/test-center.sh run` — переносимая проверка (движок на node, работает и на Windows):

- наборы `smoke` (центр + станции), `wiki` и `memory` (поиск и живые MCP-хендшейки), `bats` (все наборы
  тестов, где есть bats), `model` (живой отклик модели через `omp -p`), `persona` (живые инварианты
  персоны: зан, «домен + e2e», личный оверлей, уточняющие вопросы — 4 запроса, отключаются `--no-model`);
- недоступные наборы пропускаются с пометкой, а не падают;
- при первом сбое пишется `багрепорт.md`: система, версии инструментов, команда, код возврата,
  хвост вывода и раздел «Что проверить».

    test-center/bin/test-center.sh status        что доступно на этой машине
    test-center/bin/test-center.sh run           прогнать всё
    test-center/bin/test-center.sh report        последний багрепорт
