# plugin — команды центра в клиентах

Одна слэш-команда `/center` в трёх клиентах (opencode2, omp, pi): зовёт `center`
и показывает его вывод как есть — человеческим текстом, без JSON-простыни.
Отдельно — сводка на старте сессии (там, где для неё есть дешёвое место).

```
plugin/
  lib/center.ts      ядро: список команд, запуск центра с таймаутом, сводка
  agent/center.ts    расширение omp и pi (один файл: их API совпадает)
  opencode/center.ts плагин opencode2
  tests/plugins.bats проверка ядра, обёрток и установки
```
Установка — `../contrib/install-plugins.sh` (симлинки в каталоги клиентов); на Windows —
`../contrib/install-plugins.ps1`, та же установка на PowerShell.

## Поставить и снять

```bash
command-center/contrib/install-plugins.sh install     # ссылки в три клиента
command-center/contrib/install-plugins.sh status      # что стоит и куда ведёт
command-center/contrib/install-plugins.sh uninstall   # снять только свои ссылки
command-center/contrib/install-plugins.sh install --dry-run   # показать, не трогая
```

```powershell
pwsh -File command-center/contrib/install-plugins.ps1 install   # то же на Windows
```

Обе обёртки идут в общий движок `../contrib/install-plugins.mjs`, поэтому ставят одно и то же и
печатают одни и те же строки. Чем связать, движок решает по ОС и правам: символическая ссылка →
junction (каталоги, на Windows без прав) → копия. Про копию он говорит прямо: она за правками в
станции не следит, и после обновления плагина установку надо повторить; записанную копию повторный
`install` обновляет на месте, а `status` показывает её состояние.
Это и есть канонический вход: отдельного верба `center install-plugin` нет
намеренно — новый верб центра тянет за собой Set, usage, README и гейт доков,
то есть minor-бамп контракта, а плагины живут в своей зоне
(`command-center/contrib/**` + `plugin/**`) и ничего в контракте не меняют.

Скрипт идемпотентен: если ссылка уже ведёт сюда, он ничего не делает. Если на
месте будущей ссылки лежит чужой файл, он уезжает в `<файл>.bak`, а не в мусор;
занятый `.bak` скрипт не перезаписывает — скажет и откажется. Живые конфиги
клиентов при установке не правятся: добавляются только три новых пути.

**После установки начните сессию заново.** Список команд и скиллов клиент
снимает на старте сессии, поэтому в уже идущей сессии `/center` не появится —
ровно та же причина, по которой центр показывает `session_stale`.

## Команды

Все семь — тонкая обёртка над `center`, никакой своей логики:

| команда | что делает | таймаут |
| --- | --- | --- |
| `/center status` | что с каждым проектом: файлы, git, тесты, ссылки | 120 с |
| `/center verify` | живая проверка MCP: поднимает серверы и спрашивает их по протоколу | 300 с |
| `/center outdated` | что устарело: зовёт объявленные сверки проектов | 300 с |
| `/center update` | обновляет проекты их же командами, потом перепроверяет связи | 1800 с |
| `/center ps` | процессы станций и блокировка браузера | 30 с |
| `/center logs <проект> [--tail N]` | логи проекта | 60 с |
| `/center docs [тема]` | документация системы | 60 с |

`/center` без аргумента печатает эту же таблицу. Незнакомая подкоманда и
отсутствие обязательного аргумента — отказ **одной строкой**:

```
center: нет команды «nosuch». Есть: status | verify | outdated | update | ps | logs | docs
center logs: нужен аргумент <проект>
```
Упавший центр тоже отвечает одной строкой (`center <команда>: ошибка — <строка>`),
и только потом идёт его полный вывод: причина видна сразу.

## Сводка на старте сессии

omp и pi показывают в статусной строке (`setStatus`) одну строку (пример; версия и числа живые —
читаются из `VERSION` и файлов клиентов):

```
DATA ok · MCP omp 14/14, pi 14/14, opencode 14/14 · скиллов 84 · набор <версия> · расхождений нет
```

Пять полей: смонтирован ли DATA (читается ли VERSION набора), сколько MCP
зарегистрировано у каждого клиента, сколько скиллов в слоях, версия набора и
есть ли расхождения (MCP разошлись между клиентами, плагин центра не стоит или
ссылка битая). Меряется локально, из файлов: **замер — 2 мс** (тест держит
бюджет 2000 мс). Сводка вызывается на `session_start`; отдельного выключателя
нет. Живые соединения MCP сводка не проверяет — это дорого (поднимает серверы),
для этого `/center verify`.

**У opencode2 сводки на старте нет намеренно.** У promise-плагинов opencode нет
ни статусной строки, ни уведомлений — только сообщение в сессии, а оно мусорило
бы транскрипт в каждой сессии. Там сводку показывает `/center status`.

## Как это подключено к клиентам

| клиент | файл | API |
| --- | --- | --- |
| opencode2 | `~/.config/opencode/plugins/center.ts` | `context.command.transform` → `editor.add`, вывод — `context.session.synthetic({resume:false})` (видно в транскрипте, модель не зовётся) |
| omp | `~/.omp/agent/extensions/center.ts` | `pi.registerCommand`, сводка — `pi.on("session_start")` + `ui.setStatus` |
| pi | `~/.pi/agent/extensions/center.ts` | то же (один файл с omp: API структурно совпадает) |

Длинный вывод не обещает отдельного диалога: команда возвращает текст через
`ui.notify`, а в omp/pi статусная строка показывает только короткую сводку.

Ядро расширения грузят **динамически по своему реальному пути**, а не
статическим `import "../lib/center.ts"`: pi разрешает относительные импорты от
каталога симлинка (`~/.pi/agent/extensions/`), где никакого `lib/` нет, — и
падает на загрузке расширения, а вместе с ним и весь клиент. Реальный путь
одинаков у всех трёх, поэтому файл один и тот же.

### Чем доказано, что клиент их подхватывает

Своими же командами клиентов (полный вывод — в отчёте о работе):

```bash
# opencode2: плагин и команда
opencode2 api plugin.list  | jq -r '.data[] | select(.source.type!="builtin") | "\(.id)\t\(.state.status)"'
opencode2 api command.list | jq -r '.data[] | select(.name=="center")'
# omp: команда в списке доступных (/center будет source=extension)
printf '{"type":"get_state"}\n'     | omp --mode rpc --no-session | grep -m1 '"name":"center"'
# pi
printf '{"type":"get_commands"}\n'  | pi  --mode rpc --no-session | grep -m1 '"name":"center"'
# живой запуск команды (сессию потом удалить)
opencode2 api POST /api/session/<id>/command -d '{"name":"center","text":"status"}'
opencode2 api GET  /api/session/<id>/inbox    | jq -r '.data[-1].payload.text'
```

Тест `tests/plugins.bats` проверяет то же самое машинно (в том числе подхват
живыми `pi` и `omp`, если они стоят) плюс саму установку:

```bash
bats plugin/tests/plugins.bats
```

## Переменные окружения

| переменная | зачем |
| --- | --- |
| `CENTER_PLUGIN_TIMEOUT_MS` | свой таймаут вместо табличного (для опытов) |
| `CENTER_PLUGIN_OUTPUT_LIMIT` | предел вывода, по умолчанию 200 000 символов |
| `CENTER_NODE` | свой node вместо `node` из PATH |
| `CENTER_LINK_MODE` | чем связывать плагин при установке: `symlink`, `junction`, `copy` (список через запятую — пробуются по порядку; нужен тестам и тем, кто знает, что у него с правами) |
| `CENTER_STATE_DIR` | где движок установки помнит свои копии (по умолчанию `~/.local/state/command-center`) |
| `CENTER_ROOT_OVERRIDE` | подменить каталог станции (нужно тестам) |
