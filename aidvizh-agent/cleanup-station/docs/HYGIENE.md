# Гигиена диска данных (AGGG)

Правило, из которого всё следует:

> **На диске данных живут данные и код. Артефактам (отчёты, дампы, логи, кэши)
> здесь не место — их дом рантайм: `~/.cache/...` или `$XDG_STATE_HOME/...`.**

Причина простая: AGGG — прод-каталог, он бэкапится и переносится целиком.
Мусор в нём ломает инвентарь (сложнее понять, что тут нужное), раздувает бэкап
и путает новые сессии: непонятно, что можно удалить, а что — данные.

## Инструмент: `bin/junk-report`

Кросс-платформенный отчёт (один движок на node, обёртки под каждую ОС):

```bash
node bin/junk-report.mjs              # человекочитаемо
node bin/junk-report.mjs --json       # машинно
node bin/junk-report.mjs --strict     # rc=1, если находки есть (крон/CI)
node bin/junk-report.mjs --all        # заглядывать и в .venv/.git (по умолчанию нет)
./bin/junk-report.sh | pwsh -File bin/junk-report.ps1 | bin/junk-report.cmd
```

Что ищет:

| класс | примеры | почему мусор |
|---|---|---|
| кэши и сборка | `__pycache__`, `.mypy_cache`, `.ruff_cache`, `.pytest_cache`, `node_modules`, `build`, `dist` | регенерируются, к данным отношения не имеют |
| свалки | `_dump`, `dump`, `dumps`, `tmp`, `temp`, `trash`, `junk`, `scratch` | временные файлы живут в рантайме |
| артефакты в корне диска | `*.json`, `*.log`, `*.csv` прямо в корне AGGG | отчёт/дамп не «станция» — ему тут не место |
| служебные файлы | `*.pyc`, `*.tmp`, `*.orig`, `*.rej` | хвосты инструментов |

Тесты: `bats tests/junk-report.bats` (5 случаев: чистый диск, находки, `--strict`,
`.venv` по умолчанию пропускается, честный rc=2 на несуществующем каталоге).

## Разбор 21.09 (что было и что стало)

Нашлось два источника, оба — не «пользователь насорил», а инструменты:

1. **Конвенция `_dump` в корне диска.** `command-center/registry.json` объявлял
   `_dump` как «склад временных файлов и отчётов» — то есть сама карта разрешала
   свалку в прод-каталоге. Внутри лежал один отчёт ресёрча (13 КБ).
   → Файл переехал в `~/.local/state/command-center/dump/`, каталог `_dump` удалён,
   запись в реестре/карте/README описывает новое место и правило.
2. **Кэши инструментов внутри репозитория.** `mypy` складывал 30.4 МБ в
   `camoufox-research/.mypy_cache`, рядом жили `.ruff_cache`, `build/`,
   `__pycache__` (164–564 КБ каждый) — всё это на диске данных.
   → Удалено, а источник закрыт: в репозитории появился `scripts/gates.sh`,
   который прогоняет все гейты (ruff/mypy/bandit/semgrep/bats/unittest) с
   кэшами **вне** репозитория (`MYPY_CACHE_DIR`, `RUFF_CACHE_DIR`,
   `PYTHONPYCACHEPREFIX` → `~/.cache/camoufox-research/gates`).

Проверка, что источник закрыт, а не только подметено: полный прогон
`bash scripts/gates.sh` (все гейты зелёные, 299 тестов) — и сразу после него
`node bin/junk-report.mjs` показывает **0 находок, 0 МБ**.

## Кросс-платформенность

- движок — только stdlib Node (никаких шеллов, путей через `path.join`), поэтому
  одинаково работает на Linux/macOS/Windows;
- обёртки повторяют шаблон станции: `junk-report.sh` (Linux/macOS),
  `junk-report.ps1` (Windows PowerShell 5.1+, ASCII-вывод),
  `junk-report.cmd` (двойной щелчок);
- пути нигде не хардкодятся: диск вычисляется как родитель станции, домашний
  каталог берётся из `os.homedir()`; для тестов подменяется фикстурой;
- **проверено живьём**: Linux (этот прогон), тесты bats 5/5. Windows/macOS —
  по коду кросс-платформенно, но на живой ОС не запускалось (честная граница).

## Как поддерживать

- раз в неделю/перед бэкапом: `node cleanup-station/bin/junk-report.mjs --strict`
  (rc=1 = есть что подмести; можно повесить в крон/таймер);
- у своего инструмента, который пишет отчёты: путь из env с рантайм-дефолтом
  (`XDG_STATE_HOME`/`~/.cache`), а не «рядом со скриптом» — так делают
  `scripts/mcp_drive.py` и `scripts/soak_probe.py` в репозитории кауфми;
- новая станция = каталог в AGGG; её артефакты — уже не в AGGG.
